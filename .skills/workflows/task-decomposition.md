# 大任务自动拆解工作流

本模块将会实施的大任务拆成可验证、可依赖排序、可交接的最小工作单元。它不等于自动并行执行，也不授权修改未包含在用户范围内的项目。运行模型已判定为“查询”的同项目只读分析不加载本模块，直接在响应或项目允许的调查记录中说明拆解结论。

## 触发条件

- 任务含三个以上独立能力、模块、契约或发布阶段
- 不同部分可独立验证或由不同执行者负责
- 存在 Provider -> Consumer、数据迁移 -> 应用、基础设施 -> 功能等顺序依赖
- 复杂任务因范围太大、上下文太杂或验收不清而无法安全推进

## 拆解步骤

1. 在 spec 写主目标、Done Contract 和不可拆分约束；未验证假设留在 findings。
2. 列出不可拆分约束：共享数据、公共契约、权限、安全、发布窗口、事实源。
3. 按可验证结果切分工作单元，不按文件数量或技术名词切分。
4. 为每个单元定义输入、输出、范围、依赖、验收、风险、所有者和可否并行。
5. 形成有向依赖图，先安排阻塞最多的 Provider、基础能力或调查。
6. 检查每个单元不会产生未声明的契约变更；共享资源指定唯一负责人。
7. 先判定轻量还是 tracked：只有一个稳定 Provider 和一个明确 Consumer、同一会话、无共享写入、无交接且已有 spec/父级契约时，可将顺序直接写入该既有记录；其他拆解先启用 tracking。
8. tracked 时选择唯一落点：spec 持有共享合同和计划风险/回退；findings 持未验证假设和根因；task plan 持单元索引/依赖/负责人/当前状态；subtask 持单元合同；progress 持执行、验证、残余风险和下一步。
9. 只有 tracked 时将拆解写入 task plan；需要独立合同才使用 `.skills/templates/subtask.md`。

## 最小工作单元契约

只有一个稳定 Provider 和一个明确 Consumer、同一会话且无共享写入或交接的简单顺序，可以直接记录在既有 spec 或父级契约表中，不要求创建独立 subtask 或 task plan。出现三个以上工作单元、并行执行、独立所有者、共享写入、跨会话继续或交接时，先启用 tracking，再建立完整工作单元合同。

```text
id: T1
目标：...
范围/非范围：...
输入和事实源：...
输出与交付物：...
依赖：...
可并行：是/否，原因
验收证据：...
计划风险和回退：...
升级对象：...
```

## 并行协作规则

- 只有输入稳定、输出边界明确且不编辑相同事实源的单元才可并行。
- 共享接口、迁移、生成物、全局配置、发布脚本和任务索引默认串行或由一个协调者持有。
- 并行结果先合并为发现和验证证据，再做跨单元决策；不要把多个建议直接当成可执行事实。
- 实际变更、验证、失败、残余风险和下一步只在 progress 按子任务 ID 记录；主任务保留唯一的依赖图与完成裁决。

## 🔴 CHECKPOINT：拆解确认

执行前核对：

```text
每个子任务有唯一目标和验收
依赖图没有循环，或循环已被明确设计处理
Provider/Consumer 顺序已定义
共享写入点有唯一负责人
未授权项目和非目标没有被纳入
```

## 失败处理

| 触发条件 | 一线处理 | 兜底 |
| --- | --- | --- |
| 子任务仍然太大 | 继续按验收边界细分 | 升级为独立 complex spec |
| 发现循环依赖 | 回到契约或架构层分析 | 请求设计决策，禁止并行盲改 |
| 子任务结果互相冲突 | 以事实源、spec 和契约裁决 | 记录冲突，必要时重新 Grill |
| 并行任务修改共享文件 | 停止其中一个写入者 | 由协调者合并并重排任务 |
| 轻量拆解出现第二个执行者实施、共享写入、跨会话、交接或独立验收阶段 | 停止创建合同或行为实现 | 先启用 tracking、建立 task plan，再继续 |

## 反模式

- 以“多开执行者”为目的拆任务
- 按目录或文件数量平均分配，而不定义验收
- 让 Consumer 先假设 Provider 的未定契约
- 在 task plan 复制完整合同，或让 subtask 保存执行/验证/残余风险日志
- 把跨项目计划拆成多个无父级契约的局部任务
