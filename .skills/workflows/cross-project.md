# 跨项目协作工作流

本模块适用于多个独立项目、仓库或部署单元共同完成的任务。它把父级工作区视为契约与协调层，而不是把所有代码都放进一个“总项目”。

## 进入条件

满足任一条件时升级为 `cross`：

- 修改两个或更多独立项目
- 一个项目的公开 API、事件、数据、认证、配置、生成物或发布行为会影响另一个项目
- 需要协调 Provider、Consumer、迁移、版本、环境或发布顺序
- 需要只读检查多个独立项目，以证明契约影响、Consumer 范围或某项目确实不受影响

只读跨项目检查也必须限制在用户明确范围或工作区 registry 已登记且允许调查的项目内。范围未确认时只使用当前项目证据，并请求工作区边界；未获修改授权的跨项目影响只能调查和报告，不要自动修改相邻项目。

## 父级契约与持久化深度

父级记录放在共同工作区的项目规则指定目录，并使用 `.skills/templates/cross-project-spec.md`。父级记录始终是跨项目目标、授权范围、契约、顺序和最终一致性的真相源，但不要求每个 `cross` 任务都创建完整四件套。

工作区配置 `task_index_mode=required` 时，每个持久化父级跨项目记录还必须登记到工作区唯一任务索引。父级与本地任务保持独立编号空间；参与项目只在本级为 `required` 且本地任务已持久化时登记本地索引，为 `disabled` 时本地索引路径和锚点为 `N/A`。持久化本地任务与父级 spec 双向链接；`cross-lite` 使用内联 micro-spec 时不伪造本地文档或索引锚点，由父级 spec 直接记录项目变更或验证证据。工作区索引在 `required` 时提供同一组可达导航。Observer-only 项目不创建本地正式任务。

“参与项目”指承担修改、发布或契约交付责任的项目；“观察项目”只做获授权的只读影响核验，不计入持久化深度的项目数量。观察中确认实际受影响时，将其升级为参与项目并重新判定深度。

| 深度 | 适用条件 | 最小父级产物 | 子项目产物 |
| --- | --- | --- | --- |
| `observe-only` | 零个参与项目，只做获授权的多项目只读影响核验 | 一份调查记录，包含授权、观察项目、问题、证据和结论 | 无 |
| `cross-lite` | 一个参与项目加至少一个观察项目，或两个参与项目；且契约稳定、无 breaking/迁移/并行发布、可在单阶段完成 | 一份跨项目 `SPEC.md`，包含授权、Contract Interfaces、顺序和验证 | 仅实际修改项目按本地深度使用内联 micro-spec 或 spec |
| `cross-full` | 三个以上参与项目；任意参与项目数量且存在 breaking、迁移、版本协调、多阶段、跨会话、并行或复杂发布；或一至两个参与项目但契约稳定性/高风险条件尚未查清 | `SPEC.md` + task plan + findings + progress；交接时追加 handoff | 实际修改项目建立本地 spec，并与父级双向链接 |

按参与项目数量先判定：零个走 `observe-only`；一个或两个只有在稳定与低风险证据齐全时走 `cross-lite`，否则暂按 `cross-full` 调查且禁止实现，证据充分后可在执行 checkpoint 前降为 `cross-lite`；三个以上直接走 `cross-full`。`observe-only` 调查若确认任一项目需要修改、发布或契约交付，将其升级为参与项目并从本段重新判定，不得继续沿用只读深度。

路由判断若要求说明“是否允许实现”，必须同时列出实现前的完成条件：用户授权范围、工作区 registry、父级跨项目 spec 与 Contract Interfaces、Provider/Consumer 顺序、实际修改项目的本地执行门禁，以及 `cross-full` 时的子项目 spec 双向链接。只写“满足 checkpoint/门禁后允许”不算完成；任一条件缺失时结论必须是“仅可调查和计划”。

用户只要求多分支跨项目路由判断时，用一张紧凑表逐项给出父级深度、Observer 是否计数、实现结论和重新判定时点：`observe-only` 的实现结论固定为“不允许；不创建子项目施工 Spec”；Observer 升级为参与项目时明确旧放行失效并按新参与数与风险重判。表后只补上段统一实现门禁，再用独立的父级依赖句说明：读取 bundled workflow 前必须加载 `$sdd-riper-one`；该外部 SDD 依赖门禁不改变表内 `observe-only`、`cross-lite`、`cross-full` 深度。Skill 缺失、不可加载或版本不满足时停止并执行安装动作；只给必需依赖与停止点，不报告本次预检入口、已加载状态或证据地址。用户未要求证据时不展开 Observer 证明状态、检查命令或当前工作区事实。完成标准不要求展开模板字段、完整工作流或未请求的能力清单。

`cross-full` 推荐目录：

```text
<workspace-docs>/cross_projects/<编号>_<任务标题>/
├── SPEC.md
├── task_plan.md
├── findings.md
├── progress.md
└── handoff.md
```

目录只表达编号与任务标题；参与/观察项目、Provider/Consumer、状态、负责人和日期只写入父级 Spec Record。编号来源、标题语言和字符清理由父级 `PROJECT_RULES.md` 或 workspace 规则定义。

`observe-only` 不创建子项目施工记录。其他深度的子项目记录只写本项目施工内容；`cross-full` 的子项目 spec 必须与父级双向链接；`cross-lite` 可以从父级表格直接链接持久化 micro-spec、变更记录或验证证据，使用内联 micro-spec 时只记录实际变更或验证证据锚点。

## 必填契约

只在父级 `SPEC.md` 填写；`task_plan.md` 只引用该章节并维护当前操作状态：

| Provider | Interface / Contract | Consumer | Breaking | Migration | Validation | Owner |
| --- | --- | --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 待填写 | 是/否 | 待填写 | 待填写 | 待填写 |

同时在父级 Spec 的唯一项目注册表记录参与/观察身份、受影响与未受影响判断、本地记录、契约责任、范围判断锚点和授权动作；范围证据正文保留在 Observer 证明或 findings，不在注册表复制。再记录事实源、版本或生成来源、执行顺序、发布门禁和回退边界。纯只读跨项目验证只记录调查授权和证据；未进入实现时不要求执行 checkpoint。

## 证据与观察证明

本节是跨项目证据地址、Observer 证明和状态转移的唯一规范源；模板只承载字段。

- 父级记录内产生的证据使用 `<workspace-task-id>::<evidence-id>`。引用既存子任务证据时使用 `<project-id>/<task-id>::<evidence-id>` 并附子任务路径；裸 ID 不得跨记录根裁决状态。
- 每个 Observer 在父级记录中只保留一条当前证明，包含非影响依据、最窄相关检查和可定位证据；证据记录被检查项目的 commit/tag、只读命令或查询及结果/退出码，并在版本控制可用时记录检查前后工作树状态。Observer 不进入 Consumer 集合，也不创建施工 Spec；`observe-only` 直接在父级调查记录承载证明。
- Observer 证明状态只使用 `pending / validated / rejected / blocked / superseded`。新证据推翻结论或重试时，先把旧证明标为 `superseded` 并由新证明显式引用；确认受影响时将项目升级为参与项目，返回深度判定。
- 没有 Observer 时不设置观察门禁；否则只有每个 Observer 的当前证明均为 `validated`，才能声明这些项目不受影响。证明缺失、失败、阻塞或已被取代时，相关门禁保持未通过。
- 证据 `validated` 只表示对应验证有可定位证据，不等于任务状态 `Done`。父级发布/UAT、回退和所有适用门禁满足后，任务才能进入 `Done`。

## 🔴 CHECKPOINT：跨项目执行授权

开始任一参与项目的实现前，必须确认：用户授权范围列出了参与项目，工作区 registry 已确认，父级跨项目 spec 与 Contract Interfaces 已建立，`cross-full` 的子项目 spec 已双向链接，Provider/Consumer 顺序明确，且每个实际修改项目的执行门禁已满足。任一项缺失时，只能继续调查和计划，不修改项目代码。

## 执行顺序

1. 确认工作区 registry、参与项目与授权范围。
2. 按参与项目数量和风险判定 `observe-only`、`cross-lite` 或 `cross-full`。
3. 需要持久化且工作区 `task_index_mode=required` 时，先创建父级记录并登记工作区任务索引；编号或路径冲突时停止并对账。
4. `observe-only` 完成只读证据和父级结论后停止；发现实际影响时升级参与项目并返回步骤 2。
5. 其他深度建立或关联实际修改项目的本地记录；`cross-full` 双向链接子 spec，`cross-lite` 内联记录则由父级链接实际变更或验证证据。只为本级 `required` 的持久化任务同步任务索引锚点；`disabled` 层级和内联 micro-spec 使用 `N/A`。
6. Provider、基础设施、迁移或事实源先行；Consumer 后置。
7. 每个项目在本地规则下验证，再做跨项目契约与端到端验证。
8. 在父级 progress 记录实际改动项目、版本、验证、发布/回退时间线、残余风险和下一步；父级 task plan 只更新当前状态；父级 SPEC 只更新被采纳的跨项目合同、门禁或 Observer 证明状态；任务索引只同步带来源的生命周期摘要。

## 跨项目审查

- 请求/响应、事件、DTO、枚举、错误语义、认证、版本和生成物是否一致
- Consumer 范围是否被明确列出，而不是因为“可能相关”就全部修改
- 父级跨项目记录和 `cross-full` 子项目 spec 是否按持久化深度双向可达
- 工作区与参与项目是否分别服从本级模式：`required` 的持久任务使用独立编号和索引链接，`disabled` 或内联 micro-spec 使用 `N/A` 并由文档或证据保持可达
- Provider/Consumer 的本地验证与集成验证是否都有证据
- 配置、环境变量、迁移和回退顺序是否可执行

## 失败处理

| 触发条件 | 一线处理 | 兜底 |
| --- | --- | --- |
| 找不到共同父级或 registry | 只对当前项目分析 | 请求用户指定工作区边界 |
| required 模式下工作区任务索引缺失或编号冲突 | 停止创建父级持久任务和任何项目实现 | 修复工作区索引、编号与父级记录双向链接后重新核验 |
| 参与项目数量无法落入已选深度 | 按零个、一个或两个、三个以上重新计数 | 降回只读调查，不开始任何项目实现 |
| 一至两个参与项目的稳定性或高风险条件未知 | 暂按 `cross-full` 调查并列出待证事实 | 在事实查清前不进入实现；满足全部 lite 条件后才能降级 |
| Consumer 契约未知 | 停止 Consumer 实现 | 先固定 Provider 契约或创建兼容层决策 |
| 父级证据地址无法定位或发生冲突 | 标记对应证明 `blocked` | 改用父级地址，或补齐项目、任务与子任务路径后重新核验 |
| Observer 证明缺失、失败或过期 | 撤销或不得形成“不受影响”结论，并保持相关门禁未完成 | 补齐依据、最窄检查和新证据；不得把 Observer 改记为 Consumer 来绕过 |
| 已验证的 Observer 出现相反新证据 | 将旧证明标为 `superseded` 并撤销相关门禁 | 建立新证明；确认受影响时升级为参与项目并重新判定深度 |
| 技术验证通过但发布/UAT 未满足 | 保持任务未完成 | 满足发布/UAT、回退和全部适用门禁后才能进入 `Done` |
| 一个项目验证通过、集成失败 | 在父级 progress 记录失败与受影响门禁 | 需要根因调查时再在 findings 链接 progress 锚点，以跨项目合同测试为准重做诊断 |
| 发布顺序无法确定 | 标记发布门禁未通过 | 不宣称跨项目完成 |

## 反模式

- 将跨项目 `task_plan.md`、`findings.md`、`progress.md` 放在任一子项目根目录
- 默认所有 Consumer 都要同步，而不列明影响范围
- 把零参与项目的纯调查强行记为 `cross-lite`，或在发现实际影响后仍保留 `observe-only`
- 在稳定性或高风险条件未知时先走 `cross-lite`
- 让子项目 spec 代替父级契约
- 跨记录根引用裸证据 ID，或用一个项目的证据满足另一个项目的状态
- 把证据 `validated` 写成任务 `Done`，或在 Observer 当前证明未通过时宣称其不受影响
- 用聊天记忆代替 Provider/Consumer、迁移和发布记录
