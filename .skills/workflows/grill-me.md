# 复杂任务需求提纯工作流

本模块将 Grill 定义为 SDD 的需求提纯引擎，而不是每个任务都必须经历的访谈。已确认的合同产物回写到 spec；待查事实和未验证假设只写 findings，随后返回已加载的全局 SDD Harness。

## 何时触发

任务已分类为 `complex` 或 `cross`，且满足任一条件时触发：

- 需求存在会改变方案、数据模型、接口或用户体验的歧义
- 目标、成功标准、非目标、责任边界或决策人缺失
- 多个项目、角色、系统或外部接口之间存在冲突
- 用户提出“优化”“重构”“平台化”“自动化”但尚未定义可验证结果
- 已有方案含大量假设，且错误假设的返工成本高

`zero`、`micro` 和 `standard` 一律不启动完整 Grill。候选 `standard` 若仍有会改变方案、范围、契约或验收的歧义，先升级为 `complex`，再按本节判断。纯机械修改、用户已给出完整可验收 spec、仅需定位事实的只读调查同样不触发。

## 提纯顺序

1. **目标**：要改变的可观察结果是什么，谁受益，什么不算成功。
2. **边界**：范围内、范围外、不可触碰的兼容/安全/时间边界。
3. **事实**：已知现状、事实源、依赖、约束与证据质量。
4. **选择**：存在的方案、关键取舍、决策人和不可逆点。
5. **验收**：可观察行为、测试、人工验收、性能/安全/迁移证据。
6. **风险**：失败模式、回退、发布/数据保护和跨项目影响。

一次只追问会改变实现或验收的关键问题。优先使用已有文档和源码可验证的答案，不要求用户回答可自行查明的事实。

## 需求提纯产物

将已确认的结果写入 spec；将待查事实、未验证假设和未决问题写入 findings：

| 字段 | 内容 |
| --- | --- |
| 已确认目标 | 可观察的结果 |
| 非目标 | 明确不做的事项 |
| 已采纳事实 | 已验证事实、来源和可信度 |
| 待查事实/工作假设 | 写入 findings，附验证点或升级条件 |
| 未决问题 | 写入 findings，附影响、决策者和截止点 |
| 方案与取舍 | 被选方案、替代方案和理由 |
| 验收契约 | 通过条件、失败条件和证据 |
| 风险与回退 | 触发条件、回退动作和责任边界 |

## 🔴 CHECKPOINT：提纯完成

进入实现前，必须确认以下陈述为真：

```text
目标和非目标可区分
关键事实有来源
未决问题不会改变当前实现方向，或已获明确决策
验收方式可执行
风险与回退边界明确
```

若任一项为假，继续调查或请求用户决策；不要用“合理猜测”替代会改变方案的确认，也不要把未验证项写进 spec。

## 失败处理

| 触发条件 | 一线处理 | 兜底 |
| --- | --- | --- |
| 用户无法回答关键问题 | 说明每个选项的影响与默认风险 | 不实施不可逆部分，只完成可验证调查 |
| 问题数量不断增长 | 依据“是否改变实现/验收”排序 | 将低优先级项记录为候选待办 |
| 已有文档彼此冲突 | 标记冲突来源并比较代码事实 | 请求责任人裁决，不静默选一份文档 |
| 访谈开始重复 | 总结已确认与仍缺失项 | 停止追问，形成明确阻塞清单 |

## 反模式

- 对每个小修启动长访谈
- 把可从代码或文档获得的事实反问用户
- 把提问数量当作严谨度
- 把未确认假设写成既定需求
- 只问功能，不问非目标、验收和回退
