# 核心运行模型

所有工程任务在本文件完成分类后，由技能注册表选中的全局 SDD Skill 推进。任务分类只决定调查深度、持久化密度、执行门禁和验证强度，不决定是否启用 SDD 核心闭环。

## 任务分类

先根据用户目标和已知影响做初始分类，再按 `PROJECT_RULES.md` 选择 Bootstrap 路径。Bootstrap 只补项目事实，不改变任务分类；调查得到新证据后再按本节的升级或降级规则调整。

### 唯一路由决策

按以下顺序判断，命中第一项后停止；不得同时保留多个深度：

1. 涉及多个独立项目的修改、契约判断或影响验证时，选择 `cross`，包括只读证明某项目不受影响。
2. 未命中 `cross` 且不修改文件，只需解释、定位、审查或报告时，选择“查询”。
3. 单项目内纯机械、可逆、单点且不改变行为、渲染、契约、数据、生成物或测试语义时，选择 `zero`。
4. 单项目任务触及架构、公共契约、数据、权限、迁移、生产/外部系统、高影响未知根因或其他高风险边界时，选择 `complex`；风险已知不等于风险消失。
5. 其余单项目任务只有在目标和验收明确、低风险，且限一个实现文件及其紧耦合测试/文档时，选择 `micro`。
6. 其余会修改文件的单项目任务统一选择 `standard`。

| 分类 | 判定 | 必需动作 |
| --- | --- | --- |
| `cross` | 修改、契约判断或验证涉及多个独立项目 | 建立父级跨项目契约记录；复杂、长周期或多阶段任务再建立完整任务包 |
| 查询 | 单项目只读回答，且不涉及跨项目影响验证 | 读取证据并说明不确定性，不修改项目 |
| `zero` | 单项目机械修改，且不改变行为、渲染、契约、数据、生成物或测试语义 | 执行后给出验证或检查结果 |
| `complex` | 单项目高影响、高风险或关键不确定性任务 | 先调查；仅对会改变方案或验收的歧义启用 Grill，再建立 spec、task plan、findings、progress |
| `micro` | 单项目明确低风险修改，限一个实现文件及其紧耦合测试/文档 | 形成最小 micro-spec，写目标、范围、风险和验收；默认可内联到执行前复述与最终摘要 |
| `standard` | 未命中以上分类的其余会修改文件的单项目任务 | 建立 spec，按 SDD 推进 |

若执行中发现范围或风险上升，立即升级分类并更新持久化文档。Research 后若证据证明高影响不确定性已经消失，可以在进入 Plan 前降低分类，并记录原分类、降级证据和新的最小产物；不得通过降级隐藏已确认的公共契约、数据、权限、迁移或跨项目风险。不要为了避免规划而把复杂任务伪装成小改。

## SDD 内核与深度压缩

| 分类 | 始终保留 | 可裁剪内容 |
| --- | --- | --- |
| 查询 | Restate、Research、来源证据、不确定性和只读结论 | 不创建 spec，不进入 Plan/Execute，不制造 Reverse Sync 候选之外的长期写入 |
| `zero` | Restate、目标检查、最窄变更、验证和最终摘要 | 可不落盘 spec；发现行为或风险变化立即升级 |
| `micro` | 最小 spec、范围/风险/验收、按项目门禁执行、验证与回写 | 可按政策内联，不强制独立 task plan/findings/progress |
| `standard` | 持久 spec、必要 findings、Plan、Execute、Review、Reverse Sync | 单阶段可不建 task plan，使用独立 progress |
| `complex` | 完整 Spec Record、明确 checkpoint、三轴 Review 与恢复锚点 | Innovate、Codemap、Grill 等仍按实际信号启用，不为仪式强制生成 |
| `cross` | 父级契约、跨项目安全门禁、各参与项目本地闭环与一致性证据 | 按 `observe-only/cross-lite/cross-full` 裁剪任务包密度 |

`$sdd-riper-one-light` / `$sdd-riper-one` 是按任务模式选择的必需 Harness Skill；所选 Skill 缺失时停止当前任务并提示安装。本文件定义项目分类、产物和门禁合同，不替代缺失的全局 Skill。Codemap、Karpathy、Grill、第三方文档能力和项目私有 Skill 都是 SDD 阶段能力，不能取代主循环。

## 执行门禁

`PROJECT_RULES.md` 必须声明 `execution_gate`：

| 值 | 行为 |
| --- | --- |
| `user-intent` | 用户的明确“修复/实现/修改”请求可作为执行授权；仍要记录计划与风险 |
| `checkpoint` | 对 `standard`、`complex`、`cross` 在实现前给出短 checkpoint，等待明确批准 |
| `always-approve` | 对所有会改变行为的文件等待明确批准 |

默认模板使用 `checkpoint`，以适配严格 SDD；已有项目可以保留自己的执行政策。文档整理是否需要审批也由项目规则定义，规则文档和模板变化始终按高影响变更处理。

## 🔴 CHECKPOINT：执行前确认

在需要门禁时输出且落盘以下内容：

```text
当前理解：...
核心目标：...
范围与非范围：...
下一步：...
主要风险：...
验证证据：...
需要的决定或批准：...
```

明确批准后才进入实现。多个门禁只有在审批人相同、期间没有待决调查或规划、且所有必填决定与证据能一次列全时，才能合并为一次 checkpoint；必须显式列出该批准同时满足哪些门禁，不得因合并省略字段。若用户改变目标、范围、方案或验收，先更新 spec，再重新 checkpoint。

`micro` 的最小 spec 可以直接体现在执行前复述和最终回写中，不要求为明确、同会话、低风险的小修改单独创建文件。项目要求文件化、任务需要跨会话恢复、影响公共行为或执行中升级深度时，使用项目登记路径落盘 micro-spec。

## 完成定义

任务只有同时满足以下条件才算完成：

1. 查询已核对问题、证据与不确定性；`zero` 已核对目标和最终摘要；其他分类已核对 spec 或 micro-spec 的目标、范围和验收项。
2. 受影响代码、配置、生成物和契约已按项目规则处理。
3. 已运行或明确记录未运行的风险匹配验证。
4. 实际偏差、失败、未验证项和后续动作已回写。
5. 已完成 Project Sync Scan，并留下恢复或交接入口。

## 失败与暂停

| 触发条件 | 立即动作 | 仍未解决时 |
| --- | --- | --- |
| 需求会改变实现方向 | 停止实现，列出可选解释和影响 | 使用 Grill 或请求用户决策 |
| 验证失败 | 保存失败证据，检查目标是否仍成立 | 改变诊断路径，不重复同一失败操作 |
| 三次独立尝试仍无进展 | 回读 spec、findings 与假设 | 报告已尝试内容、阻塞和需要的外部信息 |
| 发现跨项目影响 | 升级为 `cross`，建立契约和任务包 | 未获范围授权时只分析，不修改其他项目 |
| 发现 spec 与代码事实冲突 | 先将证据和未验证解释写入 findings | 采纳结论后更新 spec；不用过期 spec 强行覆盖现状 |
