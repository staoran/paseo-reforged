## 1. 目标、范围与完成契约

- 背景/问题：`listImportableProviderSessions()` 使用 `limit + importedSessions.count`，已导入会话越多，provider discovery 请求越大；导入前后多次 `agentStorage.list()` 全扫。当前 mutation map 只把同 key 操作串行，第二个并发调用不会复用第一个成功结果，反而可能随后得到“already imported”。
- 最终目标：用 0046 的 persistence-handle metadata index 过滤已导入项，以不超过 request limit 的 bounded provider snapshot 替代 imported-count overfetch，并让相同 query/import 复用 in-flight 或短期结果；导入成功响应只在 workspace、Agent record/catalog 与 0042 Timeline 可恢复提交后返回。
- 当前任务单元：只治理导入发现、并发去重、幂等结果和导入提交恢复，不扩展 provider cursor 或用户可见 job 协议。
- 范围内：handle lookup、provider/cwd query key、bounded snapshot、in-flight/short-lived result reuse、同 handle 幂等 import、失败重试、normalized history 单次读取、轻量 import transaction marker 和 durable commit/recovery。
- 范围外：通用后台 job framework、新 progress/cancel wire、跨重启 job 队列、0046 catalog 实现、0042 store 实现、移动端测试。
- Done Contract：
  - listing 请求上限不随 imported count 线性增长；1000 个已导入 handle 不导致 `limit+1000` discovery。
  - `filteredAlreadyImportedCount` 只描述本次 bounded provider snapshot 内被过滤的数量，不再暗示 provider 全历史总数；UI 不以该值推导“仍可填满 N”。
  - 相同 provider/cwd/filter 查询并发共享工作；相同 provider handle 的并发 import 返回同一成功/失败结果，不重复创建 Agent 或 workspace。
  - 当前 provider 公共合同只有 `limit/cwd`：每个 provider 至多执行一次不超过 normalized request limit（协议最大 200）的 snapshot；过滤后允许少于 N，不在本项增加 cursor 或循环 overfetch。
  - fresh import 预分配 Agent ID；provider history 最多读取一次，先写入该 ID 的不可见 0042 working generation，再由 0046 prepared record 一次公开 record/catalog handle entry。prepared record 携带已完成的 `timelineRevision`，catalog entry 是外部可见 commit point。
  - archived restore 不复制 Timeline 或创建第二个 Agent；既有 archived record 快照是补偿源，unarchive 的 catalog mutation 是该分支的 commit point。
  - 处理失败或进程崩溃后，transaction recovery 必须确认 commit point 后完成，或补偿本事务拥有的新 workspace/Timeline/prepared record/Agent record；项目记录仅在 marker 能证明由本事务创建且仍无其他 workspace 时删除，未知所有权 fail safe 保留。
  - 现有 UI loading/error/retry 继续可用；没有 job capability 时不展示虚假百分比或 cancel。
- 失败或回炉方式：始终保持 bounded 单次 snapshot并明确结果可能少于 N；transaction marker 无法证明 commit point 时执行补偿并允许重试，不能以扫描全部 provider history、暴露 pending Agent 或新建 job framework 作为 fallback。

### 1.1 最小任务单元判断

- 为什么当前任务单元足够小：首批围绕同一个 provider-handle identity 下的 listing、in-flight import 与一次 commit/recovery workflow；0042/0046 分别拥有 raw Timeline/record 原子性，本项不新增跨连接 job protocol。
- 验证证据：`import-sessions.ts`、provider listing、workspace import 和 ImportSessionSheet 已有定向 seam。
- 模型可自主决定的范围：可选择短期成功结果 TTL 和 transaction marker 的内部文件名；provider discovery limit 固定为 normalized request limit，不得新增 cursor、缓存 settled failure、合并不同 query/ownership 或猜测 provider identity。
- 拆分决定：`Accepted；stable 后缩减`。

### 1.2 stable 影响与必要性

- stable History 搜索没有改变 import RPC 或 UI，但要求 0046 保持完整轻量 metadata catalog；该 catalog 可自然拥有 persistence-handle -> Agent identity 索引。
- 当前 `collectImportedProviderSessions()`、`importProviderSessionNow()` 和 `resolveProviderSessionImportMutationKey()` 均通过 `agentStorage.list()` 读取全部记录，若 0045 自建第二份索引会与 0046 漂移。
- UI 已有基本 loading、error 和 retry；当前没有真实时长、断线恢复或用户取消证据证明必须立刻建设 durable job/progress/cancel 协议。
- 必要性结论：`缩减保留`。保留可静态确认的 overfetch、全扫和并发结果问题；完整任务化延后为独立候选条件。
- 新依赖：0046 必须先提供统一 handle catalog 与 staged record/catalog commit seam；0042 必须提供 staging generation/complete coverage；0043 不再是 listing/import 去重的技术依赖。

### 2.2 已确认事实

- request 已携带 `requestId`，provider identity 是 `provider + providerHandleId`。
- `providerSessionImportMutations` 按 key 串行 Promise，但每个等待者仍会重新执行 operation。
- 0046 已交付 active/archived handle 检查和 mutation key 解析迁移所需的 `findByPersistenceHandle()`、catalog generation 和 prepared record seam，并通过定向与集成验证。
- listing 先计算 imported count，再把该 count 加到 provider `limit`。
- 导入 archived record 已有 rollback，新增幂等复用必须保持该事务边界。
- `AgentManager.importProviderSession()` 已经一次取得 provider history，并在首次 `agent_state` 发布前等待 record 持久化和 0042 Timeline commit；当前缺口是首次 record 早于 Timeline commit 可见，以及注册中途失败后的 live/record/Timeline 清理。
- 0042 公开 `stageRows/commit/markIncomplete/deleteAgent`，没有“只删除某个 working generation”的调用方 seam；fresh import 因预分配独占 Agent ID，可用 `deleteAgent(agentId)` 补偿整个 Timeline，archived restore 不得删除既有 Timeline。
- `runInImportWorkspace()` 只在同进程异常时恢复 workspace/project；崩溃恢复必须在创建前持久化 planned workspace ID，并在创建后记录 workspace/project 所有权证据。

### 2.3 方案与决策

| 方案                                                       | 决策 | 理由                                                   |
| ---------------------------------------------------------- | ---- | ------------------------------------------------------ |
| 0045 自建持久 handle manifest                              | 排除 | 与 0046 Agent metadata catalog 重复                    |
| 使用 0046 catalog handle index + bounded provider snapshot | 接受 | 单一所有权，直接消除全扫与 overfetch，允许过滤后少于 N |
| 同 key 串行但每次重跑                                      | 排除 | 并发调用不能共享成功结果                               |
| in-flight shared Promise + 明确短期 result cache           | 接受 | 幂等且容易用调用次数验证                               |
| 立即新增 durable job/progress/cancel RPC                   | 暂缓 | 缺少必须跨连接/取消/进度的证据，协议成本过高           |

修订决定：本任务只接受 **bounded snapshot**，不扩展 cursor。若未来需要填满 N unseen，必须先建立 provider-agnostic cursor 证据并另建任务。

#### Import commit / recovery 状态机

1. 用 0046 handle index 解析 `provider + providerHandleId`：active record 在 cwd 与显式 workspace ownership 一致时直接返回同一 Agent；archived alias 统一映射到 Agent ID；fresh identity 使用 handle key。多个索引候选沿 0046 已固定的 metadata recency/id 排序选择，若第一候选与请求 ownership 冲突则 fail closed，不静默换到另一条。相同 identity 且参数等价的并发调用共享同一 Promise；参数冲突明确失败；settled failure 从 map 删除。
2. fresh import 在任何 workspace/Agent/Timeline 写入前预分配 transaction ID、Agent ID 和可选 planned workspace ID，并持久化 marker。archived restore 的 marker 记录既有 Agent ID、完整 archived record 快照及其 record revision。marker schema 还固定 identity/request fingerprint、phase、createdAt、可选 prepared ID/record revision/timeline revision，以及 workspace ownership；marker 只用于恢复，不是 job、队列或进度协议。
3. `runInImportWorkspace()` 使用 planned workspace ID；创建后、provider import 前把 exact workspace record、此前 project snapshot（`null` 表示当时不存在）和 created ownership 写回 marker。恢复只在 workspace id/cwd/project 全匹配、且没有其他 active Agent 引用时删除 workspace；只有 previous project 明确为 `null` 且无其他 workspace 时才删除 project，previous project 为 archived snapshot 时才恢复该快照。证据缺失或已被其他对象采用时跳过删除并记录，不猜测所有权。marker 更新失败沿现有同步 rollback 路径退出。
4. fresh import 只调用 provider `importSession` 一次。AgentManager 将 rows 写入独占 Agent ID 的 0042 working generation并完成校验/commit；准备期间允许 manager 内部持有 runtime，但必须标记 unpublished，使 `listAgents()`、subscribe replay、普通 directory 与持久化 hook 均不可见。随后用 0046 `prepareRecord(absent)` 写入带相同 `timelineRevision` 的最终 idle record，并把 opaque prepared ID/revision 写回 marker。
5. `commitPreparedRecord(preparedId)` 原子公开 fresh record 与 catalog handle entry；0046 catalog 的 `preparedCommitId` 是 durable lineage，后续同 Agent 普通 upsert/setTimelineRevision 必须保留，只有 remove/rebuild 确认 record 消失时才移除。fresh 分支所有可能失败的 provider/runtime/Timeline 准备工作必须位于 commit point 前，commit 后只做不改变 durable 结论的 best-effort state 发布与 marker cleanup。archived restore 沿现有流程先 unarchive catalog、再验证 provider resume；同进程 resume 失败恢复原 record，崩溃恢复若看到 ownership 一致的 active record则把 durable unarchive 视为已提交并允许后续 lazy resume。成功响应仍等待 provider resume/live registration。
6. 同进程失败先停止未发布 runtime；fresh 分支删除独占 Timeline、未提交 prepared record、可能出现的本 Agent record和事务拥有的 workspace，archived 分支恢复原 record 快照且不删除既有 Timeline。补偿完成后才清 marker；补偿失败保留 marker并 fail closed。
7. daemon 启动在 `agentStorage.initialize()`、workspace registry bootstrap 之后、WebSocket/listening 与普通 listing 之前恢复 marker。fresh entry 只有在 agent id、handle、preserved `preparedCommitId` 和 0042 `timelineRevision` coverage 一致时判定已提交；record revision 用于 stage/commit 冲突检查，不要求后续合法 upsert 后仍等于初始 revision。archived entry 只有在同 Agent 已 active 且 cwd/workspace ownership 一致时判定已提交。其余按第 6 步补偿；补偿 IO/registry 操作失败保留 marker并让 bootstrap 失败，所有权证据不足而主动跳过未知 project 删除不视为恢复失败。核心 Agent/import 状态收敛后清 marker。
8. 同进程若发现同 identity 的未清 marker，必须先按同一判定执行 targeted recovery；无法恢复时 fail closed，不启动第二个 import。marker 文件 schema/JSON 损坏时 daemon 启动失败并保留原文件，不把未知事务隔离后继续 ready。
9. listing 以 provider set + normalized cwd + since + limit + catalog generation 为 key，共享 in-flight 并缓存成功结果 `1s`；catalog generation 变化自然失效，失败不缓存，返回前复制 payload 防止调用方污染缓存。每次 provider snapshot 的 `limit` 精确等于 normalized request limit且最大 200，过滤后允许少于 N；相同 activity 时间以 provider/id 确定排序。
