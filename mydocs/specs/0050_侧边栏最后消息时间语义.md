## 1. 目标、范围与完成契约

- 背景/问题：0034 将侧边栏 workspace 时间接到了 `Agent.updatedAt`；访问冷会话会恢复 Runtime 并推进该字段，因此当前显示接近“最后访问/状态活动时间”，不是最后消息时间。
- 最终目标：侧边栏相对时间严格以 workspace 中未归档根 Agent 的最后一条 `user_message` 或 `assistant_message` 的 canonical timeline 时间为基准，不因访问会话、恢复 Provider Runtime、工具/推理/usage 事件、状态切换或配置更新而推进。
- 当前任务单元：以独立 `lastMessageAt` 完成 persistence -> protocol -> App model/cache -> sidebar projection 全链路，并以兼容、恢复隔离和强制 history 重建证据收口。
- 范围内：Agent 持久化字段、可选 WebSocket snapshot/list 字段、server 消息时间推进与恢复规则、App Agent 归一化和 replica cache、workspace 根 Agent 聚合、侧边栏投影及定向测试。
- 范围外：History/Command Center 等既有 `lastActivityAt` 排序语义、相对时间格式化算法、0048 Hermes 修复、0049 stored-only Runtime 状态修复、0038-0046 性能任务、主 `6767` daemon、提交和发布。
- Done Contract：用户消息为 T1、助手消息为 T2、后续非消息活动或冷访问为 T3 时，server snapshot/list、持久记录和侧边栏均保持 T2；同一 workspace 多个未归档根 Agent 取最大有效消息时间；子 Agent、归档 Agent和无消息 Agent不产生显示时间；新旧 wire payload 双向接受；定向 RED/GREEN、声明构建、typecheck、lint、format 和差异检查通过。
- 失败或回炉方式：任何测试证明 canonical timestamp、旧数据兼容或恢复隔离无法由当前字段链保证时，先回到 Plan 更新兼容策略和文件边界，再继续实现；不以 `updatedAt` 或 `lastUserMessageAt` fallback 掩盖缺失事实。

### 1.1 最小任务单元判断

- 为什么当前任务单元足够小：任务只新增一个正交时间事实并沿既有 persistence -> protocol -> App projection 链传播，不改消息内容、timeline 顺序、相对时间算法或其他活动排序。
- 验证证据：三个既有 public seam 可独立构造确定性输入并观察 payload、持久记录和 sidebar projection。
- 模型可自主决定的范围：在已列文件和 seam 内选择最小 helper、测试夹具和兼容表示；不得改变消息集合、恢复 Runtime 策略或其他 `lastActivityAt` 消费者。
- 拆分决定：`Accepted`；这是一个跨 workspace package 但单仓库、单契约链的原子修复，不另拆子 Spec。

### 2.2 调研结论

- 已确认事实：`normalizeAgentSnapshot()` 当前执行 `lastActivityAt: updatedAt`；`buildWorkspaceAgentActivityIndex()` 聚合未归档根 Agent 的最大 `lastActivityAt`；`registerSession()` 和任意 live event 会推进 `updatedAt`；冷会话 `ensureAgentLoaded()` 会恢复 Runtime，因此访问会话会改变当前侧边栏基准。
- 已确认事实：`lastUserMessageAt` 只覆盖用户消息，不能表示更晚的助手消息；canonical message 时间来自 `AgentTimelineRow.timestamp`，history/import 可携带 provider timestamp。
- 已确认事实：Agent snapshot/list schema 由 protocol Zod schema 生成 AOT validator，新增字段必须 optional/nullable，不能使用 transform/catch/preprocess。
- 诊断反馈环：首个 Seam B 定向测试将直接断言 T1 用户、T2 助手、T3 非消息活动后的 public Agent 状态和持久记录；它是快速、确定性、可由 Agent 独立运行且能精确复现本缺陷的 red-capable loop。
- 根因假设排序：H1（已由源码确认）App 将 `updatedAt` 别名为 sidebar activity；H2（已由源码确认）workspace 聚合继续消费该通用活动字段；H3（已由源码确认）server 没有助手消息级独立事实且冷恢复推进 `updatedAt`；H4（已排除为本任务根因）相对时间 formatter/Hermes 差异由 0048 独立处理。
- 未知与开放问题：`None`；旧记录和旧 daemon 的缺失字段策略已在本 Plan 固化为“未知即 null，不伪造”。
- 风险与约束：旧记录可能没有可直接取得的助手消息时间；只能在活动恢复已加载 canonical durable rows 时补算，stored-only/归档记录不得为此恢复 Provider Runtime。assistant 分片、history replay、import 和系统生成的 `assistant_message` 都要使用 row timestamp 单调合并。并行 dirty diff 必须保留。
- `grilling` 结论：`N/A`；消息类型、无消息行为、聚合范围和兼容策略均已明确。

### 2.3 方案与决策

- 备选方案：A. 复用 `lastUserMessageAt`；B. App 扫当前 timeline；C. 新增独立 `lastMessageAt`；D. 继续使用 `updatedAt` 并过滤部分 touch。
- 已选方案：C。`lastMessageAt` 从 canonical timeline row 写入 `ManagedAgent`，持久化到 `StoredAgentRecord`，以 optional/nullable 字段投影到 snapshot/list，再归一化到 App Agent 和侧边栏 workspace 聚合。
- 选择理由：只有独立事实能同时覆盖用户与助手消息、冷会话和 stored-only 列表，并与状态/工具/访问活动彻底正交；无需扫描 App timeline 或改变通用 `updatedAt` 行为。
- 兼容决策：旧 payload/旧记录缺字段时归一化为 `null`，不回退 `updatedAt` 或 `lastUserMessageAt`；新 daemon 恢复活动 Agent 时可从已经加载的 canonical durable timeline rows 补算，不能仅为该字段恢复 Provider Runtime。新字段 optional/nullable，旧客户端忽略新字段，新客户端接受旧 daemon 缺字段。
- Innovate：`Skipped`；候选方案已由语义完整性和公共数据链唯一确定，无需额外架构分叉。
