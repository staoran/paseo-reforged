## 1. 目标、范围与完成契约

- 背景/问题：当前 E2EE 已协商 `binaryCiphertext`，但 JSON 等字符串消息仍以 Base64 WebSocket text 传输，额外增加约 33% 表示开销；终端实时输出和大多数 `agent_stream` 是小而密集的低延迟流，不适合逐帧压缩；远端后上线时的 timeline、Agent、Workspace、Provider 和终端状态追平会产生较大、重复度高的数据，完成态的大型 `tool_call` 也可能携带高重复输出，适合在加密前独立压缩。
- 最终目标：新 client 与新 daemon 通过协商后的认证 envelope 传输所有 E2EE 应用帧；默认使用 WebSocket binary 消除文本密文 Base64，也允许显式选择 framed Base64；只对 daemon 发往远端的 `state-sync`、明确可压缩的 `bulk` 和通过严格门禁的 `bulk-live` 帧按配置尝试 raw DEFLATE，并保持其他实时路径、direct WebSocket、应用业务消息、旧版本互通和 relay 零知识边界不变。
- 当前任务单元：0087–0095 的 wire、codec、FIFO、runtime、分类、client、Desktop 与 metrics/benchmark 均已独立 GREEN；下一单元为 0097 的混合版本、真实环境和长期文档收口。
- 范围内：E2EE capability/selection 协商、加密前 envelope、Base64/binary 密文表示、raw DEFLATE adapter、`daemon.relay.transport` 配置及 Desktop 控件、daemon 出站 `realtime/state-sync/bulk/bulk-live` 流量分类、完成态大型 `tool_call` 门禁、FIFO 与高水位、严格解压限额、客户端解压、观测指标、真实数据 benchmark、混合版本与 live relay 验证、相关安全和架构文档。

- 失败或回炉方式：若仅 Hermes `deflate-raw` 解压门禁失败，该 client 从 `compressionAlgorithms` 移除 codec，但仍可 advertisement framed identity；若 envelope、消息顺序、Base64/binary 表示、32 MiB relay 限额、64 MiB 物理发送高水位或混合版本验证失败，才停止 advertisement `framedCiphertextV1` 并保持现有 `binaryCiphertext`/Base64 路径。不得以静默猜测、放宽限额或压缩实时帧绕过失败。

### 2.2 调研结论

#### 已确认事实

- `EncryptedChannel` 当前只在 `binaryCiphertext` 协商成功且原始数据是 `ArrayBuffer` 时发送 raw binary ciphertext；字符串仍被 Base64 后作为 WebSocket text 发送。
- 当前 NaCl bundle 是 `[24-byte nonce][ciphertext + 16-byte MAC]`，固定加密开销 40 字节。
- server 的 encrypted relay socket 在真正发送前用 `outboundWireByteLength()` 估算 wire 长度；引入异步压缩后必须改成只准备一次、按最终长度检查再发送。
- 源码的物理发送高水位是 64 MiB；`docs/architecture.md` 仍写 8 MiB，属于本任务需同步的现有文档漂移。生产 relay 的单帧 wire 限制为 32 MiB。
- timeline 实时路径是 `agent_stream`；权威追平路径是 `fetch_agent_timeline_response`，每页目标 40 个投影条目，单个 canonical shell tool output 上限为 64 KiB。
- 终端输出由 5 ms coalescer 合并；`Output` 是实时流，`Snapshot`/`Restore` 是状态恢复；只有累计输出超过 256 KiB 且 transport backlog 超过 4 MiB 时才进入 snapshot catch-up。
- 文件传输的 `FileChunk` 为 256 KiB；`FileBegin` 已携带 `encoding` 和 MIME，因此发送端无需解析文件内容即可决定是否允许尝试压缩。
- `permessage-deflate` 发生在应用加密之后，对高熵密文基本无收益，也无法表达“实时不压缩、追平才压缩”，因此不是可选实现。
- production relay 已能透明转发 Base64 text 与协商后的 binary ciphertext；新 envelope 无论采用哪种 WebSocket 表示都保持 opaque，不需要 relay 解密、压缩或识别业务类型。
- 当前 mutable relay config 只包含 `relay.enabled`，由 `packages/protocol/src/messages.ts` 的 config RPC schema、server persisted config、`DaemonConfigStore` 和 Desktop 配对界面共同维护；新增 transport policy 必须沿用 `daemon.relay`，不能在 pairing offer 或各发送点建立第二份配置真相源。
- 旧 daemon 的 mutable relay schema 是 `.passthrough()`，但持久化 relay schema 是 `.strict()` 且只回写 `enabled`；因此新 App 若不经过独立 capability gate 向旧 daemon 写 transport 字段，会出现“响应看似成功但重启后丢失”的假成功。

- JSON 样本按 `31.56 MB` 输入和 `18.8 MB/s` 粗算约需 `1.7 s` 压缩 wall time；省下 `26.05 MB` wire，在不考虑流水重叠时的理论 break-even 约为 `124 Mbps`。该值是模型估算，不是端到端实测；典型远程弱网有净收益，快速 LAN 必须由门禁验证。

- Hermes 解压 p95、GC、峰值内存与耗电尚未实测，是 advertisement 上线前的阻塞验证项。

#### 未知与开放问题

- 真机 Hermes 上 `fflate.inflateSync` 对 1 MiB/4 MiB frame 的 p95 和 UI stall 尚未知。
- 现有 level 1/3/6 数据只覆盖编码；同一原文由不同 level 生成 bitstream 后的 Node/Hermes 解码差异尚未实测，不能假定耗时完全一致。
- production relay 对连续 framed Base64/binary frame 的实测吞吐和边界行为需由现有 live relay E2E 验证；若不透明转发，只报告跨项目阻塞，不在本任务修改外部服务。
- 当前真实终端 wire size 分布缺少内容无关的聚合采样；实施后由 runtime metrics 补齐，不记录 plaintext。

#### 风险与约束

- 异步压缩/解压会使消息完成顺序变化；发送和接收都必须显式 FIFO。
- framed 接收可能在异步解压期间继续到帧；必须在 Base64 解码/解密前校验 raw wire 长度，并按 raw wire bytes 为当前处理项和等待队列统一预留，防止慢 decoder 形成无界内存队列。
- 压缩前后长度关系会加强 relay 可观察的尺寸侧信道；不使用共享字典或跨帧 context，只压缩独立且随后整体认证的应用帧，并在安全文档保留残余风险。
- `originalLength` 不能让压缩帧绕过原有逻辑上限；必须同时限制原始长度、wire 长度、压缩比和解压输出。
- Node async zlib 使用 libuv worker pool；大量并发追平可能与其他 worker-pool 工作争用。`compressionCodecMs` 只能观测从调用 adapter 到 zlib callback 的 wall time，其中包含可能的 worker-pool 等待，不能独立拆出 worker queue 与纯 codec；`compressionQueueMs` 另行表示 encrypted socket 的发送 FIFO 等待，不能把两者混为一谈。
- 新 framed mode 对原本已是 binary 的 terminal/file 帧增加 8 字节 envelope 开销；实时 binary 不压缩，因此需要用真实帧分布确认该固定开销可接受；选择 Base64 还会承担精确的 4/3 表示开销。
- `ciphertextEncoding` 只能在握手时锁定；连接中途切换 WebSocket text/binary opcode 会制造无法判定的 mode 边界。压缩开关不改变 envelope 解释，可在已经协商 framed 的连接上更新。
- v1 固定 level 1 仍会增加状态帧准备时间，并可能通过严格 FIFO 间接延迟其后的实时帧；`bulk-live` 因与实时消息共享连接，必须使用更高的 16 KiB 下限、相同的两个非等待压缩槽和实时回归门禁。
- “level 不进入 wire”只表示 decoder API 与 wire 解释无需知道发送 level，不表示解码免费或各 level 成本恒定。接收端仍会消耗 inflate CPU、内存和分配；不同 level 产生的流长度、匹配与 Huffman 结构不同，解码耗时可能略有变化，通常只比编码端对 level 不敏感，必须以 `inboundDecodeMs` 实测。
- 新字段持久化到现有严格 `config.json` 后，回退到不认识这些字段的旧 daemon binary 可能拒绝启动；实现必须避免在无关 patch 中主动物化默认 transport block，并在配置文档写明旧版本回退前删除该 block。wire 版本回退仍自动，配置文件回退不是无条件自动。

### 2.3 方案与决策

- 备选方案 A：对所有 E2EE 帧使用 WebSocket `permessage-deflate`。否决，因为它压缩的是密文、收益接近零，且不支持业务语义分类。
- 备选方案 B：所有 plaintext 在 NaCl 前统一压缩。否决，因为小而密集的实时帧有额外 CPU、排队和尺寸扩张风险。
- 备选方案 C：保持现有 wire，只把大 JSON 手工 gzip 后塞进业务消息。否决，因为会污染 `packages/protocol`、重复 text/binary 处理并让每个业务域自行兼容。
- 已选方案：E2EE transport 内部 `framedCiphertextV1`；所有新模式应用帧使用固定 8 字节认证 envelope，连接级选择 Base64 text 或 binary wire；按集中解析出的 transport policy 与发送端 `trafficHint` 决定是否对 payload 使用独立 raw DEFLATE；legacy 路径完全保留。
- 配置方案：`daemon.relay.transport` 只增加 `ciphertextEncoding: "auto" | "base64" | "binary"` 与 `compression.enabled`。v1 不提供用户可选 algorithm、strategy 或 level：encoder 内部固定 `deflate-raw level 1`，逐帧选择由 traffic class、分类专属下限、4 MiB 上限、最小收益、压缩比和 CPU 槽位共同决定；wire codec 仍只有 `identity` 与 `deflate-raw`。
- 选择理由：认证 envelope 与 WebSocket 表示解耦后，Base64 可作为兼容/诊断选项且不牺牲状态压缩；当前只有一个实际 codec，而 level 3/6 的边际带宽收益不足以抵消配置、热更新、测试与支持成本；语义分类与固定门禁不能被用户绕过；单一 policy resolver 防止各发送点各自解释策略；能力协商仍允许未来以 additive codec 滚动升级。
- Innovate：`Completed`；实际流量收敛为 `realtime`、`state-sync`、`bulk` 与 `bulk-live` 四分类，配置、wire、协商和 adapter 方案见附录 A-D。

### 6.2 性能与安全门禁

- 分类正确性：`realtime` 的 `compressionAttemptCount` 必须为 0；未知消息必须归为 realtime；只有 `agent_stream.payload.event.type === "timeline"`、`item.type === "tool_call"` 且 `item.status === "completed"` 才可标记 `bulk-live`，其他 assistant/reasoning 增量及 running/failed/canceled tool-call 均为 realtime；`bulk-live` 序列化后小于 16 KiB 时不得调用 compressor。
- 数据正确性：所有 text/binary round-trip byte-for-byte；多帧顺序与调用顺序 100% 一致；任何长度、codec、UTF-8 或 MAC 错误都关闭当前物理连接。
- 带宽：默认 `auto`（framed binary）相对当前 legacy 的真实 JSON corpus 最终 wire 至少节省 50%，真实 UTF-8 文件至少节省 60%；强制 framed Base64 相对 legacy Base64 的 JSON/文本 wire 至少节省 35%；JPEG/WebP/PNG/binary 文件的压缩采用次数为 0。
- 弱网：在 2 Mbps/150 ms 与 10 Mbps/80 ms profile 上，40-item timeline catch-up 和 10 MiB 文本下载的 p50/p95 完成时间相对 legacy 至少改善 20%。
- 实时：并行发生状态追平或 `bulk-live` 压缩时，terminal echo 与增量 `agent_stream` p95 相对 legacy 的回归不超过 `max(2 ms, 5%)`；若超过，回到 Plan 调整准备队列、`bulk-live` 下限或压缩上限，不能扩大实时压缩范围。
- Daemon CPU：内部固定 level 1 在 i7-4790 同类基线的全链路 framed+deflate prepare 吞吐不低于 15 MB/s；event-loop p99 不因 native zlib callback 增加超过 5 ms。benchmark 可分别报告 level 1/3/6 的 CPU、wall time、采用率和实时 p95，但 3/6 仅为研究变量，不进入 runtime adapter、配置或兼容契约；改变固定 level 必须回到 Plan 并重新验证。
- Hermes：1 MiB frame 解压 p95 不超过 50 ms，4 MiB 不超过 150 ms；无 OOM、无超过 expected output 的分配、无可观察错序。仅 codec 门禁失败时该 client 不 advertisement `deflate-raw`，但通过 envelope/encoding 门禁后仍可 advertisement framed identity。
- 限额：发送端只压缩 4 KiB 至 4 MiB 原始 payload，其中 `bulk-live` 下限单独提高为 16 KiB；收益至少 `max(64 bytes, 5%)` 且压缩比不超过 128:1；接收端在 Base64 decode/decrypt 前执行 32 MiB raw wire 上限，当前处理项与等待 FIFO 的 raw wire reservation 合计不超过 64 MiB，解密后仍执行原始 text/binary 逻辑上限。
- 观测：指标只包含计数、字节、class/codec/skip reason 和耗时；不得记录 payload、文件名、路径、请求正文、公钥以外的握手内容或 secret。
- 配置：缺省值解析为 `encoding auto / compression enabled`；runtime 内部固定 `deflate-raw level 1`，persisted/RPC/UI/configured/effective policy 均不存在 algorithm、strategy 或 level 字段；`enabled=false`、legacy mode 或 peer 不支持 `deflate-raw` 时压缩采用次数均为 0，并记录不同 effective reason；活动连接不得中途改变 encoding。
- 回滚：关闭新 capability advertisement 或回退任一通信端后，混合版本自动恢复现有 wire；若曾把 `daemon.relay.transport` 写入 `config.json`，回退到不识别该严格字段的旧 daemon binary 前需删除该 block，此限制必须进入发布说明。

- 集成验证：以同一真实 dataset 比较 legacy、framed identity、framed deflate；再在真实 relay 上执行状态追平期间的终端交互和文件下载。
- 剩余风险：压缩尺寸侧信道不能在不加 padding 的前提下完全消除；生产 relay 外部代码仍只读验证；Hermes、真实 Desktop packaged smoke、并行 realtime p95 和 hosted relay 近 32 MiB 两种表示边界尚未完成。
- Done Contract 是否由证据满足：`No`；live relay、弱网与统一代码审查已满足，第 6.1 的 mobile/realtime/hosted 近 32 MiB 边界仍阻塞，不能将 0084 标为完成。

## 附录 A：流量分类与实时行为

分类只在发送端结构化序列化位置产生，不依据 heartbeat、双方在线状态或 payload 大小猜测。在线状态可能陈旧，且同一连接会同时承载追平与实时消息；traffic class 描述消息语义，不描述连接状态。

| 业务帧                                                                               | class                                    | v1 codec 策略                                    | 具体原因                                     |
| ------------------------------------------------------------------------------------ | ---------------------------------------- | ------------------------------------------------ | -------------------------------------------- |
| `agent_stream` assistant/reasoning 增量及非 tool-call timeline                       | `realtime`                               | 始终 `identity`                                  | 保持增量首包和 token 流延迟                  |
| `agent_stream` running/failed/canceled `tool_call`                                   | `realtime`                               | 始终 `identity`                                  | 运行与异常状态优先低延迟                     |
| `agent_stream` completed `tool_call`                                                 | `bulk-live` + compressible               | 仅序列化后 16 KiB-4 MiB 且全部门禁通过时尝试     | 完成态大输出可降带宽，不压缩进行中增量       |
| terminal `Output/Input/Resize`                                                       | `realtime`                               | 始终 `identity`                                  | 5 ms 合帧，小而密集；输入/resize 更小        |
| ping/pong、hello、status、控制帧、未知消息                                           | `realtime`                               | 始终 `identity`                                  | 控制面优先且默认安全                         |
| `fetch_agent_timeline_response`                                                      | `state-sync`                             | 配置启用、4 KiB-4 MiB 且收益达标时使用有效 codec | 远端追平和分页历史重复度高                   |
| `fetch_agents_response`、`fetch_agent_history_response`、`fetch_workspaces_response` | `state-sync`                             | 同上                                             | 冷启动/恢复目录状态                          |
| `get_providers_snapshot_response`、`providers_snapshot_update`                       | `state-sync`                             | 同上                                             | snapshot 结构重复                            |
| terminal `Snapshot/Restore`                                                          | `state-sync`                             | 同上                                             | 完整 cell-grid/ANSI 恢复，不是交互 delta     |
| file `FileChunk` + `encoding === "utf-8"`                                            | `bulk` + compressible                    | 每个 256 KiB chunk 独立尝试                      | 文本文件真实样本收益高                       |
| binary FileChunk                                                                     | `bulk` + not compressible                | `identity`                                       | v1 不猜 binary MIME                          |
| FileBegin、FileEnd                                                                   | `realtime` + not compressible            | `identity`                                       | 控制帧太小，不进入 compressor                |
| client→daemon 任意帧                                                                 | 语义可保留，v1 sender policy 为 identity | `identity`                                       | 首版不在 Hermes 做压缩；上传优化后续另行批准 |

即使 state-sync 小于 4 KiB、压缩被禁用、peer 不支持 configured codec 或压缩无收益，它仍可走协商后的 framed Base64/binary，但 codec 为 identity。认证 framing、密文表示与压缩是三个独立层。

`bulk-live` 只是发送端本地 traffic class，不写入 envelope、capability 或应用消息。receiver 无需知道该分类，只按已认证的 `codec` 与通用解压限额处理；因此它不增加 wire 版本或跨设备兼容矩阵。completed tool-call 即使被标记为候选，只要序列化后不足 16 KiB、超过 4 MiB、无空闲槽、收益不足、压缩比超限或 adapter 异常，都立即以 identity 进入原 FIFO，不能等待压缩槽。

## 附录 B：配置与有效策略

### B.1 公共配置 shape

```json
{
  "daemon": {
    "relay": {
      "transport": {
        "ciphertextEncoding": "auto",
        "compression": {
          "enabled": true
        }
      }
    }
  }
}
```

| 字段                  | 类型/范围                        | 缺省值 | 暴露层级 | 契约                                                                                 |
| --------------------- | -------------------------------- | ------ | -------- | ------------------------------------------------------------------------------------ |
| `ciphertextEncoding`  | `"auto" \| "base64" \| "binary"` | `auto` | 普通 UI  | 选择同一 XSalsa20-Poly1305 密文的 WebSocket 表示，不更换加密算法；协商结果按连接锁定 |
| `compression.enabled` | `boolean`                        | `true` | 普通 UI  | 只控制允许分类的 daemon 出站帧；实时帧仍恒为 identity                                |

- v1 runtime codec 固定为 `deflate-raw`，不在 persisted/RPC config 中定义 `algorithm` 或 `strategy` 字段。`auto` 不再作为压缩配置值；逐帧采用与否始终由附录 A/D 的语义分类、尺寸、收益、比率和 CPU 门禁决定。
- `gzip` 与 raw DEFLATE 使用同一核心算法，却增加 wrapper、CRC 和长度开销；envelope 已认证且携带原始长度，因此 v1 不为制造选择加入 gzip。
- Brotli/zstd 需要新的 Web/Hermes runtime、bundle/WASM 与真机门禁；以后新增算法必须先扩展 capability/codec 与兼容矩阵，再决定是否需要配置，不能重解释 `deflate-raw` 或提前放置无效 algorithm enum。
- persisted config、config RPC、所有 UI、configured/effective policy 和 diagnostics 均不定义 level 字段。v1 daemon encoder 私有常量固定为 level 1；level 3/6 只能由 benchmark 直接调用 codec 作为研究对照，不能经生产 adapter 或配置注入。
- persisted 与 RPC schema 的字段保持 optional，默认由 resolver 在内存中补齐；新 home 和仅修改 `relay.enabled` 的旧 home 不主动写出 transport block。用户第一次明确修改任一 transport 字段后才持久化该 block。
- `PASEO_RELAY_ENABLED` 与 `--relay/--no-relay` 仍只覆盖 `relay.enabled`。v1 不新增 transport env/CLI precedence；即使 enabled 被 launch override 锁定，transport policy 仍可修改和持久化。
- pairing offer/QR 不携带 transport policy。它只包含建立连接所需的 endpoint/TLS/public key；每个 data socket 在 E2EE hello/ready 中独立协商实际 wire。

### B.2 三层状态

```text
ConfiguredRelayTransportPolicy
  + LocalRelayTransportCapabilities
  + PeerE2EECapabilities
  -> NegotiatedRelayTransportPolicy (connection immutable)
  -> EffectiveRelayTransportPolicy (compression policy may update)
```

| 层         | 示例                                                                              | 生命周期与用途                                                                                |
| ---------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| configured | `encoding=binary, compression={enabled:true}`                                     | 来自 `daemon.relay.transport`；只表达用户可设置的 encoding 与开关                             |
| negotiated | `mode=framed-v1, encoding=binary, compressionAlgorithms=[deflate-raw]`            | hello/ready/confirm 后对当前 data socket 锁定；不得因配置变化中途切换 opcode 或 envelope 解释 |
| effective  | `encoding=binary, compression={enabled:true, algorithm:deflate-raw, reason:null}` | resolver 注入固定 codec 后的输出；legacy、禁用或 peer 不支持时包含明确 reason                 |

有效 compression 的 connection-level 禁用原因至少区分 `configured-disabled`、`legacy-mode`、`peer-unsupported`；逐帧 skip reason 继续区分 `traffic-ineligible`、`too-small`、`too-large`、`no-gain`、`ratio`、`busy`、`error`。不得把所有情况折叠为 `identity` 而失去诊断依据。

### B.3 配置应用时机

| 配置变化              | 已建立 framed 连接               | 后续新连接   | 已建立 legacy 连接                |
| --------------------- | -------------------------------- | ------------ | --------------------------------- |
| `compression.enabled` | 下一出站帧生效                   | 使用新值     | 保持 identity，原因 `legacy-mode` |
| `ciphertextEncoding`  | 不变；返回“已保存，后续连接生效” | 按新偏好协商 | 不变，不做中途 upgrade            |
| 内部 codec/level/策略 | 非配置；随当前实现版本固定       | 重新协商能力 | 保持 identity                     |

- 在 relay 连接本身提交 encoding patch 时，set response 与后续帧仍按该连接原 mode 发送；不能在 config response 前后静默换 opcode。
- 已开始的 compression job 固定使用启动时的 codec/enabled snapshot 和内部 level 1 并按原 FIFO 完成；开关更新只影响尚未开始的 frame，不能取消后把半成品当 identity 发送。
- Desktop 只有在 `server_info.features.relayTransportPolicy === true` 时才读取/写入新控件；现有 `relayConfig` capability 只代表可修改 enabled，不能推断 transport policy 支持。
- UI 只使用 encoding segmented control 与 compression toggle；不显示也不接受 algorithm、strategy 或 level。状态需区分“当前连接”与“后续连接”，不能把 configured binary 显示成当前连接已经 binary。

## 附录 C：能力协商与兼容状态机

### C.1 明文握手能力

以下为 default `auto` 与完整能力 client 的示例；显式 `base64` 时 ready 选择 Base64 且省略 `binaryCiphertext`：

```text
e2ee_hello.capabilities = {
  binaryCiphertext: true,
  framedCiphertextV1: {
    ciphertextEncodings: ["base64", "binary"],
    compressionAlgorithms: ["deflate-raw"]
  }
}

e2ee_ready.capabilities = {
  binaryCiphertext: true,
  framedCiphertextV1: {
    ciphertextEncoding: "binary",
    compressionAlgorithms: ["deflate-raw"]
  }
}
```

- hello 的 `ciphertextEncodings` 表达 client runtime 可发送且可接收的 framed wire 表示；`compressionAlgorithms` 表达 v1 daemon→client 方向可解码的 codec。`identity` 是 framed v1 内建必选项，不放入列表。
- ready 中的 `ciphertextEncoding` 是 daemon 按 configured policy 与 offer 选出的唯一连接级表示；`compressionAlgorithms` 是双方共同支持的有序集合。共同 codec 集合允许为空，此时 framed identity 仍可用，不能仅因无压缩 codec 退回 legacy。
- codec 集合只反映本地 encoder/peer decoder 的已验证能力，不受当前 `compression.enabled` 过滤；这样关闭后重开可以热生效，并为未来 additive codec 保留协商空间。Hermes 只在通过真机门禁后才 offer `deflate-raw`。
- 每个 framed capability 数组最多接受 16 个 token，每个 token 最多 64 个 UTF-16 code units；未知但在界内的 token 可忽略。hello offer 任一数组越界或结构畸形时只把 `framedCiphertextV1` 视为缺失，保留已验证的 hello key/type 与 legacy capability；ready 任一数组越界或结构畸形时 fail closed。ready 只能选择 hello 实际提供的 encoding 和 codec。
- `ciphertextEncoding=auto` 优先 `framed-v1-binary`，peer 不提供 binary 但提供 framed Base64 时选择 `framed-v1-base64`；`base64` 只选择 framed Base64 且不 echo legacy `binaryCiphertext`；`binary` 只选择 framed binary，peer 不提供时回退 legacy，不偷偷改用 framed Base64。
- 没有 framed 共同 encoding 时保持 legacy：`auto/binary` 可在 peer offer `binaryCiphertext` 时沿用当前 hybrid wire，`base64` 或缺少该能力时使用全 Base64。显式 binary 是兼容优先的偏好，不因旧 peer 断开；diagnostics 必须显示实际降级结果。

### C.2 无额外完整 RTT 的 mode confirm

1. Client 收到带 selection 的 plaintext `e2ee_ready` 后，先用现有 legacy Base64 密文表示发送内部 confirm：`{ type: "e2ee_mode_confirm", mode: "framed-ciphertext-v1", ciphertextEncoding, compressionAlgorithms }`。字段必须语义上逐项 echo ready selection。
2. Client 等 confirm 的 transport send 完成后切换 framed 状态。握手期间积压的应用 send 必须先按原调用顺序接入发送 FIFO，再触发应用 `onopen`；`onopen` 回调中新产生的 send 只能追加在这些帧之后。confirm 本身永不压缩，也不使用新 envelope。
3. Daemon 发送 framed selection 后暂不向 WebSocketServer 暴露 open；它通过同一 receive FIFO legacy-decrypt 第一帧。只有 exact confirm 才锁定 selection 并 attach；任何普通应用帧、伪 confirm 或 selection 不匹配都按协议错误关闭，不能在 pending selection 状态静默改锁 legacy。
4. WebSocket 顺序与 receive FIFO 保证 daemon 总在 framed 应用帧之前处理 confirm，因此不需要 daemon→client 的额外 ack RTT。不能只依赖 async callback 恰好按完成顺序返回。
5. Relay 在 hello 到达 daemon 前删除 framed offer 时，daemon 从未产生 selection，双方可按保留下来的 legacy capabilities 正常降级。若 daemon 已选择 framed，ready selection 被删除、添加或改写都会因缺少 exact authenticated confirm 而 fail closed；不能把可检测的 ready 篡改降级为 legacy。

`e2ee_mode_confirm` 是 transport 保留消息，任何状态下都不能上交应用层。无 pending selection 却收到 confirm、pending selection 后首帧不是 exact confirm、confirm 与保存值不同，或 framed 锁定后以 legacy opcode 重放 confirm，均关闭连接。这样 relay 对 ready 单向删除、添加或改写 selection 时会失败，而不是把内部消息误交给 WebSocketServer 或静默降级。

重复同 key 的 `e2ee_hello` 仍按当前逻辑重发 ready 且不 re-key；ready 必须重发该连接已经保存的 selection。连接一旦 attach，重复 ready/hello/confirm 都不能触发 in-place mode、encoding 或 key 变化。

## 附录 D：认证 envelope 与 codec 算法

### D.1 加密前格式

```text
byte 0      magic = 0x50
byte 1      version = 0x01
byte 2      flags: bit 0 = original payload is binary; bits 1..7 = 0
byte 3      codec: 0x00 = identity; 0x01 = deflate-raw
byte 4..7   originalLength: uint32 big-endian
byte 8..N   encoded payload
```

这 8 字节不是 wire 明文；header 与 payload 一起进入现有 XSalsa20-Poly1305。最终 wire 是：

```text
[24-byte nonce][encrypted(header + encoded payload) + 16-byte MAC]
```

因此加密前后 framed 固定开销是 48 字节：现有 40 字节加密开销 + 8 字节 envelope。连接锁定后的最终表示为：

```text
framed-v1-binary wire bytes = encodedLength + 48
framed-v1-base64 wire bytes = 4 * ceil((encodedLength + 48) / 3)
```

WebSocket opcode 不写入 header，因为它是连接级 selection；receiver 必须按锁定值接收，binary mode 收到 text 或 Base64 mode 收到 binary 均为 protocol error。framed Base64 必须使用标准 padded Base64、无空白，并在分配前校验 alphabet、padding 和 exact decoded length；hello/ready 仍是 plaintext text，mode confirm 仍是 legacy Base64 ciphertext text。

### D.2 固定策略常量

```text
MIN_COMPRESSION_BYTES = 4 * 1024
MIN_BULK_LIVE_COMPRESSION_BYTES = 16 * 1024
MAX_COMPRESSION_INPUT_BYTES = 4 * 1024 * 1024
MIN_COMPRESSION_SAVINGS_BYTES = 64
MIN_COMPRESSION_SAVINGS_RATIO = 0.05
MAX_COMPRESSION_RATIO = 128
MAX_CONCURRENT_DAEMON_COMPRESSION_JOBS = 2
FIXED_COMPRESSION_ALGORITHM = deflate-raw
FIXED_DEFLATE_LEVEL = 1
MAX_FRAMED_WIRE_BYTES = 32 * 1024 * 1024
MAX_PENDING_FRAMED_RECEIVE_WIRE_BYTES = 64 * 1024 * 1024
```

- 只有 effective compression enabled，协商集合包含内部固定的 `deflate-raw`，且为 `state-sync`、`bulk && compressible` 或 `bulk-live && compressible`，才允许进入 compressor；peer 不支持时使用 identity 并记录 `peer-unsupported`。不存在用户可覆盖的 algorithm、level 或“强制压缩”策略。
- `bulk-live` 只允许来自 completed `tool_call` 的结构化 hint，序列化后还必须位于 16 KiB-4 MiB；其他 class 使用通用 4 KiB-4 MiB。分类错误、尺寸不符或未知事件都不得调用 compressor。
- 采用压缩结果需满足 `compressedLength <= originalLength - max(64, ceil(originalLength * 0.05))`。
- 若压缩结果过大、压缩比超过 128:1、adapter 暂时不可用或 compress 抛错，记录 skip reason 并安全回退 identity；不关闭连接。
- daemon compression 使用进程级两个非等待槽；没有空槽时不排队，记录 `busy` 并直接发送 identity，避免追平 burst 占满 libuv worker pool。
- 每帧独立 raw DEFLATE，daemon encoder 私有实现固定 level 1；无 gzip/zlib wrapper、共享 dictionary 或 context takeover。level 不写入 envelope，decoder API 和 wire 解释不依赖发送 level。
- receiver 仍必须执行 bounded raw inflate，并承担 CPU、内存和分配成本。不同 encoder level 可能产生长度、匹配和 Huffman 结构不同的合法 DEFLATE bitstream，因此解码耗时不保证完全一致；运行时必须测 `inboundDecodeMs`，安全限额也不能依赖“level 1 解码更便宜”的假设。
- v1 client→daemon envelope 只允许 `codec=identity`；daemon 收到其他 codec 直接按协议错误关闭，不能因为本地恰有 inflate adapter 就扩大首版上传契约。
- `codec=identity` 必须满足 `encodedLength === originalLength`；`codec=deflate-raw` 必须在 inflate 前满足 original、encoded、ratio 与逻辑上限。text/binary 均先按现有原始业务上限校验，最终 Base64/binary wire 再严格小于 production relay 32 MiB，不能用压缩授权更大的业务对象。
- receiver 对 `deflate-raw` 同样要求 `originalLength` 位于 4 KiB-4 MiB，且 encoded length 达到最小收益门槛并未超过 128:1；不满足即在 inflate 前关闭，不能让 peer 绕过 sender policy 消耗 decoder CPU。

### D.3 发送顺序

```text
structured message / binary frame
  -> attach trafficHint before serialization is lost
  -> normalize UTF-8 bytes and original binary flag
  -> validate original logical length
  -> optionally deflate once
  -> select identity/deflate from actual savings
  -> build authenticated envelope
  -> NaCl encrypt once
  -> encode as locked Base64 text or keep binary
  -> obtain exact wireByteLength
  -> FIFO capacity check against bufferedAmount + reserved bytes
  -> WebSocket send with locked opcode
```

- 每个 encrypted socket 维护单一发送 FIFO；异步压缩完成先后不能改变调用顺序。
- 入队时通过 channel 的 representation-aware wire 计算按 identity 上界预留 pending bytes；该上界包含 8 字节 envelope、NaCl 开销和 Base64/binary 最终表示，不能只用原始 payload 长度。准备完成后原子替换为最终 wire reservation，再做第二次精确高水位检查，并在 `finally` 释放。
- `bufferedAmount` 对上层返回 physical buffered + preparing identity-wire reservation + prepared final-wire reservation，使现有 64 MiB backstop 覆盖尚未写入 socket 的工作；preparing 转 prepared 时原子替换，prepared 只在内层 channel FIFO 即将同步调用物理 `transport.send` 的 handoff callback 中移除，既不留下未计账窗口，也不重复计入同一 wire。
- direct WebSocket 继续走现有同步发送，不创建 envelope，不压缩，也不解析 hint。

### D.4 接收顺序

```text
WebSocket text or binary matching locked selection
  -> validate raw wire length and strict Base64 shape without allocating decoded output
  -> reserve raw wire bytes in bounded receive FIFO
  -> when at FIFO head, Base64 decode when selected
  -> authenticated decrypt
  -> validate magic/version/reserved flags/codec/originalLength/wire limits
  -> identity copy or bounded raw inflate
  -> require exact output length
  -> restore ArrayBuffer or fatal UTF-8 string
  -> existing application callback
  -> release receive reservation in finally
```

- raw binary `byteLength` 或经 ASCII alphabet/padding 预检后的 Base64 text length 必须先满足 32 MiB wire 上限；Base64 必须在 decode 前由字符数和 padding 算出 exact decoded length，并验证其也不越界。不得依赖 production relay 代替端侧检查。
- 当前处理项与等待项的 raw wire bytes 都计入单连接 receive reservation；合计将超过 64 MiB 时立即关闭。错误、关闭和 adapter reject 路径都必须释放 reservation，不能因异常永久占用预算。
- Node inflate 使用 `maxOutputLength = expectedLength + 1`；fflate 使用 `out = new Uint8Array(expectedLength + 1)`。`fflate` 在输出超出预分配时会截断，因此多一字节后必须要求结果长度精确等于 `expectedLength`。
- opcode/selection 不匹配、非法 Base64、未知 magic/version/保留位/codec、identity 长度不等、压缩比超限、inflate 失败、长度不匹配或非法 UTF-8 都按协议错误关闭当前连接。
- 不能在解压失败时把 payload 当 identity，也不能在 framed 失败时回猜 legacy。

Server/client runtime metrics 至少提供以下无内容字段：

```text
configuredPolicy{ciphertextEncoding,compressionEnabled}
negotiatedModeCount{legacy-base64,legacy-hybrid,framed-v1-base64,framed-v1-binary}
effectiveCompressionCount{enabled,algorithm,reason}

```

其中 `compressionQueueMs` 是从应用调用 encrypted socket send 到该帧的有序 FIFO operation 开始之间的等待；它不是 libuv worker queue。`compressionCodecMs` 是从调用 raw DEFLATE adapter 到 zlib callback 的 wall time，可能同时包含 worker-pool 排队和 codec 执行，当前实现不声称能将两部分拆开。

`diagnostics.request` 的 relay transport snapshot 同时返回 configured policy、按 mode/encoding/codec 聚合的 active connection 数和 effective reason；不得返回 connection ID、peer key、payload 或路径。runtime metrics 的 label 集合必须是上述有界 enum，不能加入 server/client/user 标识。

Benchmark 脚本要求：

- 输入路径必须由操作者显式传入，不能默认扫描 `$PASEO_HOME`、home 或整个 workspace。
- JSON 按真实 WebSocket serialization 边界计数；completed tool-call 同时按实际 `agent_stream` 边界统计 16 KiB 门禁命中率；terminal 可分别按捕获边界和 256 B/1 KiB/4 KiB 重分帧；file 保持 256 KiB chunk。
- 对每个 corpus 输出 legacy Base64/hybrid、framed Base64 identity/deflate、framed binary identity/deflate 的 plaintext/encoded/encrypted/wire 总量、压缩采用率、p50/p95/max frame size、吞吐和 wall time。
- 默认按生产内部 level 1 完整运行；研究模式可让 level 3/6 至少对 JSON、completed tool-call 与 UTF-8 file corpus 运行，用于量化边际带宽收益、CPU 和 FIFO 等待，不能只报告压缩率。研究参数直接进入 benchmark codec，不得复用 persisted/RPC schema 或生产 runtime adapter，也不构成配置候选。
- 预热后至少运行 5 次，报告中位数和环境：OS、CPU、Node、runtime、encoding/codec/level；不得输出样本内容、原始路径或逐消息文本。
- 真实数据只做本地 benchmark；单测 fixture 使用合成数据，不能提交用户会话副本。
