## 1. 目标与完成契约

- 当前理解：设置页混用了“整轮处理过程”和“单项详情”两个层级；截图中的工具卡虽然各自详情已收起，工具列表仍逐条铺开。用户要求明确两层职责，并把工具操作按“运行命令、读取文件、编辑文件”等类型分组折叠。
- 核心目标：让设置文案准确描述外层 Activity Fold 与内层推理/工具详情；让普通时间线和按需加载的 Activity 详情都使用固定的工具分类组外层，并由同一设置控制组和组内详情的默认开合。
- Done Contract：
  - `autoExpandActivity` 展示名改为“完成后保持整轮过程展开”，描述为“轮次完成后仍展示过程文本、推理、工具调用和计划；关闭时整轮过程会收起为一条完成记录”。
  - `autoExpandReasoning` 展示名改为“默认展开推理与工具详情”，描述为“控制整轮过程内部的默认状态：开启时展开推理块、工具调用分组及组内详情；关闭时默认收起”。内部存储键保持不变，也不改变 Activity 外层状态。
  - “摘要”和“完整详情”两种模式都保留按类型分组的固定外层结构；摘要模式在展开组内显示紧凑调用行，完整详情模式显示每次调用的完整输入、输出和错误。
  - 只合并相邻同类型调用；类型被其他内容或其他工具类型隔开时另起一组。例如 `shell, shell, read, edit, edit, shell` 形成四组并保持原始时间顺序。
  - `autoExpandReasoning=true` 时工具分类组和组内工具详情均默认展开；为 `false` 时两层均默认收起。设置变化立即清除当前已挂载组和子项的手动开合状态，之后仍可手动开合，直到下一次设置变化。
  - 运行中的工具组遵守相同设置；组收起时仍展示类型、数量和运行状态，且运行更新不改变组的稳定位置或引发布局跳动。
  - 普通时间线与 `ProjectionDisplay.activityFolds[].members` 使用同一工具分组合同；折叠组展开后仍按原顺序查看每次调用，final answer、计划、`speak`、Activity 外层折叠和手动开合语义不变。
  - Shell 命令语义分类先忽略开头的 `rtk` / `rtk.exe` 包装层；`rtk read` 按读取文件、`rtk rg` / `rtk grep` / `rtk find` 按搜索识别，`rtk proxy <command>` / `rtk run <command>` 继续识别其直接子命令。只解析首个顶层命令，不递归解释 `powershell -Command`、`sh -c` 等内嵌脚本文本。
  - 定向 Vitest、根 typecheck、lint、20 个目标文件格式与差异检查通过；隔离 Web smoke 覆盖设置、Activity、分类组、文件入口和提交布局，不启动或重启主 daemon `6767`。

## 2. 范围与事实

- 范围内：`packages/app` 设置文案、工具调用分类与分组投影、按需 Activity 详情成员的投影接线、对应纯投影/分组测试。
- 范围外：修改设置存储键或迁移用户设置、删除“工具调用显示”选择、协议与 daemon、Activity 详情传输、跨项目改动、提交与发布。
- 当前任务单元：一个 App 展示层行为单元；设置文案负责解释层级，工具投影负责落实分组。
- 轻量评估：`standard`；涉及多文件但边界集中在既有设置资源与工具投影模块，不改变 wire contract 或持久数据。
- 已确认事实：
  - `autoExpandActivity` 只决定已完成 `ActivityFold` 的整轮展开状态；运行中的 Activity 始终展开。
  - `autoExpandReasoning` 经 0064 已同时投影为单条 `thought` 与普通 `tool_call` 的 `defaultExpanded`，旧文案只写“推理”已不符合实现。
  - `toolCallDetailLevel="detailed"` 当前直通逐条工具卡，`overview` 才建立折叠组；用户已确认两种模式都改为固定分类组外层，模式差异只保留在组内信息密度。
  - 当前 `overview` 把一段连续工具调用合成一个混合摘要，不按类型切组。
  - 持久会话摘要只在顶层 `ProjectionDisplay.items` 放 Activity placeholder；真实过程成员后加载到 `activityFolds[].members`。`AgentStreamView` 只对顶层 `items` 调用 `projectToolCallDetailLevel()`，随后直接渲染未投影的 fold members，因此 Activity 内的工具调用绕过分组。
- `diagnosing-bugs` 结论：0064 只控制单条工具详情的初始开合，没有折叠工具列表；本次截图的结构性根因是 Activity 详情成员没有进入工具摘要投影。现有测试只覆盖顶层 tail/head，未覆盖加载后的 fold members。
- 用户决策：`Q1-Q6=A`；Q7 要求命令文本分类排除 RTK 包装干扰。上述 Done Contract 已将其具体化为只去除开头包装层和 `proxy/run` 直连层，不解析任意嵌套脚本。
- 风险与未知：不同类型全局归并会打乱执行时间线，因此只归并相邻同类型调用；需要同时保持跨 retained tail/live head 的稳定 host、Activity 原始 `memberIds` 的跳转/revision 语义，以及折叠组内部调用的原始顺序。命令分类采用保守白名单，无法可靠识别的命令继续归为“运行命令”。
