## 1. 分类和比较标准

| 分类           | 判断标准                                                            | 本轮处理方法                                             |
| -------------- | ------------------------------------------------------------------- | -------------------------------------------------------- |
| 同源修复冲突   | 同一个原始修复通过 cherry-pick、等价 patch 或可追溯移植重复进入双方 | 去重，只保留一个实现，再检查移植差异                     |
| 同缺陷独立修复 | 修复同一可复现问题，但没有同源 patch 证据                           | 比较覆盖范围、状态所有权、失败行为与已有回归测试         |
| 同目标演进     | 用户目标相同，一方重构了职责位置或补齐生命周期                      | 用更完整的结构承载另一方已验证的细节，不保留两套权威实现 |
| 并行改动       | 两种能力或测试碰巧改到同一位置                                      | 各自保留，重建正确结构                                   |
| 真实意图冲突   | 最终行为、交互或发行政策不同，原样不能同时成立                      | 分别说明目的与代价，按已确认推荐实施并记录取舍           |
| 派生物冲突     | 版本、lockfile、依赖哈希等由上层决定                                | 先定 manifest 与发行策略，再生成，不能任选一边           |

`git log --cherry-mark --left-right --no-merges 本地...上游` 没有 `=` 等价项，结合关键提交和 PR，**没有确认到严格意义上的同源重复修复**。这不证明历史上绝无移植，只说明本轮没有证据支持把任何冲突按重复 patch 直接删除。

几个容易误分的地方：

- C33–C35 是上游提取共享状态函数碰上本地优先级修复，属于同目标演进；上游结构更好，本地判定更完整
- C49 双方都想让明确打开目标生效，但分别用 `host` 与 `placement` 表达；上游目的地模型更好，本地保留现有 sheet 身份的细节更好
- C31、C32、C63 是不同回归测试的插入冲突，不是重复测试
- 重启状态 S01 看似都在“修状态”，实际对历史状态的持久化含义不同，属于真实意图冲突
- Nix 许可证和品牌同处一块，不代表本地有坚持 AGPL 的意图；根 manifest 已是 Apache-2.0

## 2. 双方意图分别说明

### 2.1 本地 Reforged

本地保留独立产品身份、更新地址和每个已发布 beta 的记录，控制自动 CI 成本，browser E2E、桌面打包和 Nix 检查以手动触发为主。

交互合同包括：已读 idle Workspace 仍在 Ready；未读只控制绿点和标题强调；侧栏时间取真实用户或助手消息；关掉普通 Agent 标签要执行对应关闭/归档，成功后才加入关闭历史，失败保留标签和重试；历史恢复优先成为普通标签，并保护已打开预览的未保存状态。

最近两个本地提交不能被当成旧代码忽略：`9764d2259` 区分 daemon shutdown 与用户关闭，保留关机前历史驻留状态；`0886c6b53` 串行化关闭流程并保留归档会话的 Workspace 消息时间。这些都在本轮上游分叉以后，直接决定 S01 和 C67 的选择。

### 2.2 上游 Paseo

上游 0.13.0 扩展到跨主机委派、统一 Explorer 与折叠设备布局、插件文件面板及其状态保存，同时修复冷启动丢标签、compact 未读 Workspace 恢复、完成通知跨重启丢失等问题。

其状态设计把重启后无进程的 `running/initializing` 记录修成 `closed`，让消费者不要把死进程看成运行中；侧栏新增 Created / Last prompt / Manual，并默认 Created，项目默认显示七条及全部非 Done 项；Command Center、标签与侧栏共用展示职责。

上游的发行版本、自动八分片 browser CI、桌面打包自动触发、折叠 beta changelog 政策服务于上游仓库。代码修复与这些仓库政策需要分别选择。

## 9. 无文本标记的行为与交互冲突

### S01 重启后的历史驻留、操作终态和完成通知

**涉及。** `bootstrap.ts`、`agent-manager.ts`、`agent-projections.ts`、`bootstrap.smoke.test.ts`，以及上游新增 `agent/finish-subscriptions/internal/{observation,observation-stream,observation-buffer}.ts`、重启恢复测试。

**本地意图。** `9764d2259` 在 shutdown 使用 `closeAgent(id, {reason: "shutdown"})`，runtime 真正释放后仍把关机前状态持久化；重启时 `runtimeAttached: false` 表明没有进程，历史状态用于驻留和橙色提示。显式关闭仍写 closed，未完成 initializing 注册不保留驻留。`lastStatus` 在这套设计中同时承载历史信息，不等于 live provider 的事实。

**上游意图。** #7573 针对 #5951 等“重启后仍显示 running、provider 操作等待”的问题，在 storage initialize 后调用 `closeStaleAgentRecords()`，把持久化 running/initializing 改 closed，再交给状态消费者。相同 PR 还避免 Claude SDK close 被永不结束的 interrupt/return 挡住，保证进程树能清理。#7683 在这些修复之后恢复 finish watch，不自动恢复 child 工作，让父 Agent 得知 child 已结束运行。

**组合后的确定影响。** 当前预演同时保留本地 shutdown 历史持久化和上游 startup 改写。于是 running 历史重启后被抹为 closed，而 idle/error 多数仍保留，驻留语义不一致；Git 不会报这一层冲突。`bootstrap.smoke.test.ts` 还自动合并出两条 `AgentStorage` import，是确定的重复声明问题。

**不能只删 startup 修复。** 新 `createFinishObservation` 在 child 不在 manager 时从 stored payload 构建 `final`；`openFinishObservation` 的 buffer 拒绝把 `final.status` 为 running/initializing 的 initial result 当成已完成。历史 running 加无 runtime 时没有后续 turn event，若直接取消 startup 修复而不调整观察投影，父 Agent 可能无限等待。即使 manager 已加载一个 `lifecycle: closed, session: null` 的历史壳，序列化仍可能透出 `storedLastStatus`，也要覆盖。

**已确认方案（D03）。**

1. 保留本地“历史驻留”和“runtime 是否存在”的区分，不用一次 startup 批量覆盖抹掉历史；initializing 未注册完成的残留可按上游规则终结
2. 在 finish observation/操作快照边界使用 manager 的实际 lifecycle 与 runtime 所有权；对已确认没有运行时的 stored-only child，向完成观察提供 settled/closed 结果，持久化历史值保持原意，error 仍表达 error
3. 同样覆盖本机与 routed host 的已知 detached snapshot；旧 host 没有明确信息时不要凭空推断远端已终止。保留上游连接中不消耗失败次数、失败三次报告 unknown、removed host 立即结束观察等政策
4. 不改变一般 timeline/detail 读取为“为了观察就启动 provider”；不自动重跑 child；不把通知的“运行已结束”说成“用户任务已完成”
5. 审计新增 status-only 消费者，尤其 MCP list/status 过滤与 finish buffer；历史 running 不应被当作 live 运行能力。改完同步 `docs/agent-lifecycle.md` 中“先修 stale 再恢复 watch”的实际约束
6. 保留上游 Claude SDK 及时清理进程的修复，去掉重复 import。重写 startup 和 shutdown 测试的预期边界，不能只删断言凑绿

D03 已选择上述组合规则，需要同时调整启动修复与观察边界；任一原实现原样都不能满足全部目标。完全采用上游 closed 语义并另存历史驻留的替代方案未采用，因为会扩大协议/存储模型改动。

**实现比较。** 上游对 live 终态与通知恢复更完整；本地对用户历史驻留的区分更完整。不能说一方整体胜出。上游 process cleanup 可独立直接吸收，不需要和存储语义一起回退。

**最窄验收。** 正常 shutdown 与异常终止分别覆盖历史 running/idle/error/initializing；重启不启动 provider；显式关闭确实清驻留；pending finish 恢复后通知父级，ack/remove 后再次重启不重发；已加载历史壳也不挂起。注意上游 shutdown Claude 测试断言成功关闭的运行中 child 存储为 closed，与本地保留 pre-close running 的预期不同；失败/停滞 peer 的保留预期需单独看，不能把所有 shutdown 都改同一个值。
