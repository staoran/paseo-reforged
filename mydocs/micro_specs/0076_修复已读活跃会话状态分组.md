## 1. 目标与完成契约

- 当前理解：侧边栏按状态分组时，真正运行中的会话属于 `Working`；没有 running 贡献但仍有 `idle` 的会话属于 `Ready to review`，且已读不会改变这一归类。当前共享映射把 `idle + 已读` 错误降为 `done`。
- 核心目标：按 `running > idle > unread > read` 的决策顺序分组：running 为 `Working`；无 running 但有 idle 时，无论已读/未读均为 `Ready to review`；无 idle 时未读仍为 `Ready to review`，只有已读才为 `Done`。
- Done Contract：真实状态分组流程证明打开并读完 idle 会话后仍停留在 `Ready to review`，重新运行时进入 `Working`，关闭/移除 idle 且已读后才进入 `Done`；共享协议映射、daemon workspace 聚合和 App 投影一致；受影响的单文件测试、typecheck、lint、目标格式及差异检查通过。

## 2. 范围与事实

- 范围内：agent 生命周期到 workspace status bucket 的共享映射、状态分组回归测试、对应生命周期文档。
- 范围外：状态组排序与文案、attention 清除时机、terminal bucket、agent 归档/关闭交互、协议 schema 或 RPC 形状。
- 当前任务单元：修复“idle 是否进入 Ready 被错误绑定到未读标记”这一条状态转换，并锁定 running、idle、无 idle + 未读、无 idle + 已读四类边界。
- 轻量评估：`standard`；改动集中于一个共享纯函数，但同时影响 daemon、新旧 workspace 投影和用户可见分组语义，需要跨层定向验证；不改变 wire schema。
- 已确认事实：`clearAgentAttention` 只清除 `requiresAttention` 并保留 lifecycle；修改前的 `deriveAgentStateBucket` 先识别字面量 `running`，再仅以 `requiresAttention` 决定 `attention`，因此 `idle + 已读` 会回退为 `done`；daemon `WorkspaceDirectory` 与 App/legacy workspace 都复用该函数；没有 agent 贡献的 workspace descriptor 默认是 `done`。
- `grilling` 结论（如使用）：`N/A`；用户明确给出了状态转换目标和无 agent 边界。
- 风险与未知：这是共享状态语义变化，新 daemon 会让旧客户端也把已读 idle agent 保持在 `Ready to review`；需保留 `running -> running`、`closed + 已读 -> done` 与 `initializing + 已读 -> done` 的现有合同，并检查 `statusEnteredAt` 相关断言是否受影响。
- RED 证据：修正后的四格断言要求 idle 已读/未读均为 `attention`、running 为 `running`、closed 已读为 `done`；当前稳定失败为 actual `done`、expected `attention`。同环境既有协议测试为 `8 passed`。
- 假设结论：H1“共享 bucket 映射错误地把 idle 是否进入 Ready 绑定到 requiresAttention”已由修正后的直接断言、调用链和源码证实；H2“清除已读改变 lifecycle”、H3“App 分组丢失 idle”均由实现边界排除。
