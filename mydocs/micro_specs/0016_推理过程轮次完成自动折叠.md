## 1. 目标与完成契约

- 当前理解：用户所称“推理过程”是最终回答前的完整 agent activity，不是协议中的 `reasoning` 单项。它包含 reasoning、过程文本、工具与文件操作、命令、计划、todo、重试及状态消息；最终回答始终位于折叠区外。
- 核心目标：保留按 user turn 投影的 activity fold 与三套独立展开状态，但把外层展示改为 Codex Desktop 的 activity 模型：完成态显示“已处理 + 时长”，展开后每个工具条目仍显示自身类型并可独立折叠。
- Done Contract：活动中的过程始终展开；仅收到 `assistant_message.phase === "final_answer"` 后才进入完成态；完成态默认值由持久化的 `autoExpandActivity` 决定，当前会话允许手动覆盖；完成后的外层头不显示 `Thinking`，而显示本地化的“已处理 + 实际轮次时长”；`autoExpandReasoning` 与工具详情状态均不受外层 fold 影响；展开 activity 必须继续使用每个成员的既有 renderer，Read/Search/Edit/Shell 等工具显示自身类型、默认详情状态并可单独展开/收起；最终回答和待用户操作始终可见；重开会话按持久化设置重新投影；失败或中断且没有最终回答的轮次不自动折叠。

### 延后备注：历史 Activity 可重放性（不属于 0016 当前实现）

> 范围声明：`2026-07-31` 用户要求只把以下调查结论与方案记入 0016，并允许登记 TODO；本节不重开 0016、不改变当前 Done Contract 与 `Completed` 状态，也不授权实现 durable timeline、旧会话迁移或性能改造。

#### 新发现与分层结论

- 新症状：已结束的 Codex 会话在 Agent/daemon 重新加载后，展开 activity 可能只剩 `Thinking` 与 `Edit`；这不满足完整恢复 Read/Search/Shell/Plan 等既有 activity 类型的产品预期，但不否定本任务已经完成的 activity/reasoning/tool 三层 UI 展开状态隔离。
- 数据源直接原因：真实 session 的原始 rollout 含 `91` 个 `custom_tool_call` 与 `2` 个 `function_call`；同一 session 连续两次 `thread/read` 都只返回 `userMessage: 2`、`reasoning: 21`、`agentMessage: 20`、`contextCompaction: 1`、`fileChange: 2`，没有 command、MCP、search、plan 等历史 item。重开后的 `Thinking` 来自 `reasoning`，`Edit` 来自 `fileChange`；Paseo mapper 无法恢复上游没有提供的类型。
- Paseo 代码缺口：`AgentManager` 已有可选 `durableTimelineStore` 和 live `AgentTimelineRow` 写入 seam，但生产 bootstrap 没有注入持久化 Adapter；注册恢复目前也只读取 durable `latestSeq`，没有把完整 `epoch + rows + nextSeq` 回灌到客户端实际读取的内存 timeline。因此这是“Codex 历史投影有损”触发、“Paseo 未完成自身可重放持久化”放大的组合问题。
- 权威源原则：未来若实施，应以 Paseo live 阶段已经规范化的 timeline 为已管理会话的历史权威源；durable 非空时不再无条件混入 `thread/read`，durable 为空的导入/旧会话才回退 provider history 一次，避免重复、乱序和工具生命周期倒退。
- 旧会话边界：新持久化不能从残缺的 `thread/read` 凭空补回既有 Read/Search/Shell/Plan。若必须修复历史会话，只能等待上游提供完整历史，或另立兼容性任务对 Codex 私有 rollout 做显式、可验证的一次性回填；后者不应混入最小 durable timeline 实现。

#### 候选方案与成本备注

- 候选最小架构：复用现有 `AgentTimelineStore`，实现独立于 Agent 快照 JSON 的按 Agent 追加式文件 Adapter；保存版本、epoch 与 normalized committed rows。恢复时加载完整 seed，生产 bootstrap 注入该 Adapter；显式 refresh/rewind 必须先完成候选历史读取与校验，再替换 durable 数据，不能先删后读。
- 数据量：会额外保存一份 normalized timeline，但不复制原始 rollout、token delta 或原始 RPC。以本次约 `91` 个工具调用估算，平均每个持久化输出 `4-16 KiB` 时约增加 `0.4-1.5 MiB`；若每个 shell 输出都达到现有 `64 KiB` 截断上限，仅 shell 输出约 `5.7 MiB`，reasoning、assistant 文本、非 shell 工具和元数据另计。以上仅为数量级估算，不是该 session 的实测结果。
- 实时流畅性：UI/live stream 应先更新，文件追加在后台按 Agent 串行并按时间或字节阈值批量处理；只在 `turn_completed`、Agent 关闭和 daemon 退出边界等待 flush，避免每个流事件同步等待磁盘。
- 加载时间：最小实现首次重开仍按 timeline 文件大小线性顺序读取；当前系统本来也会拉取完整 provider history 并放入内存，本地读取通常可减少 RPC 成本，但超长会话仍需用真实 fixture 测量，不能预设无成本。
- 内存与清理：durable Adapter 只长期保留 epoch、latest seq、文件偏移和必要尾项等小型索引，避免与 `InMemoryAgentTimelineStore` 同时缓存第二份完整 rows。删除 Agent 时同步删除 timeline；归档为保留历史而保留 timeline，并明确本地明文工具输出的隐私与备份边界。
- 暂不引入数据库或压缩：仓库当前没有现成 SQLite 依赖；在体积与加载实测前不扩大为数据库迁移或压缩格式。若完整读取达到可感知延迟，再单独评估索引分页和 finalized turn 压缩。
