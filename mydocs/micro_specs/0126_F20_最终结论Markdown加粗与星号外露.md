## 1. 目标与完成契约

- 当前反馈：最终结论中有些 `**加粗**` 没有呈现为加粗；需区分文字已被解析但字重不足，以及 `**` 字符直接显示两种现象
- 核心目标：助手正文的 strong 使用 700 字重；对本次确认的相邻标点与文字输入做有限容错，使流式、完成及历史重载后均呈现为加粗文字
- Done Contract：用真实失败输入固定回归，修复字面 `**` 外露，同时保留转义星号、代码中的星号和原始消息内容

### 真实会话与复现

- 会话：`d8932956-2cbb-4d62-9137-d11737f44c26` 的最终结论。用户报告的页面显示与 Codex 会话原文摘录一致：`**外发员工预请款要单列一条线。**例如财务先给员工运营款 300 元，员工现场付承运方 220 元，再退回 80 元`
- 修复前 `createAssistantMarkdownParser().renderInline()` 对该句保留两侧 `**`；闭合 `**` 后插入空格则生成 `<strong>外发员工预请款要单列一条线。</strong> 例如…`
- `markdown-it` 将 `。**例` 中的双星号判为 `open: true, close: false`：前接标点、后接文字不满足其闭合分隔符规则。消息在进入解析器前仍保有原始星号；完成态和历史重载都使用普通助手解析器，故不是流式补全或字重造成的外露

### 容错边界

- 仅在助手 Markdown 解析器中，对已被 `markdown-it` 识别为 `close: false` 的双星号分隔符、前一文本以标点结束且后一 token 为连续普通文本的候选闭合标记，放宽其 `close` 判定；配对和 strong token 仍由 `markdown-it` 处理
- 保留普通合法 strong、流式未闭合标记、转义星号、行内与围栏代码的现有行为；其他 Markdown 表面继续使用原解析规则
- 不改 Provider 输出、原始消息或纯文本复制内容，不在字符串层全局插空格或剥除星号；富文本复制与界面共用助手解析器
- 这是针对代理输出的 Markdown 容错，遇到多个相邻双星号时可能存在配对歧义；用回归输入限定预期行为
