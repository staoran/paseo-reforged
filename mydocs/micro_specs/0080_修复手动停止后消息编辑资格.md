## 1. 目标与完成契约

- 当前理解：正常完成的最后一条纯文本用户消息可编辑，但用户在 turn 运行期间手动 Stop 后，同一条用户消息在 agent 回到 idle 时没有恢复 Edit 入口。
- 核心目标：让手动停止后的最后一条已确认纯文本用户消息在 agent 回到 idle 后重新取得安全的编辑资格，同时保持运行中、附件消息、未确认消息和只读状态的既有 fail-closed 门禁。
- Done Contract：现有 Playwright public seam 证明运行中不显示 Edit；手动 Stop 并回到 idle 后，刚发送的纯文本用户消息显示 Edit 且可打开预填原文的编辑器；附件消息仍不可编辑；定向回归、typecheck、lint、format 与 diff 检查通过。

## 2. 范围与事实

- 范围内：强化现有 Edit Playwright Stop 场景；定位 Stop 后编辑资格丢失的实际边界；最小修复该边界并运行相关回归。
- 范围外：放宽附件、图片、历史消息、optimistic 消息或运行中消息的编辑资格；修改公共协议；重启或修改生产式 `6767` daemon；commit、push、发布。
- 当前任务单元：只闭合“发送纯文本消息 -> 运行中无 Edit -> 手动 Stop -> idle 后 Edit 恢复”这一条用户路径。
- 轻量评估：`standard`；行为表面集中，但可能跨 App 投影与 daemon durable timeline，需要先用真实 public seam 确认边界。
- 已确认事实：`packages/app/e2e/browser/edit-last-user-message.ui-contract.spec.ts` 的第二个场景现已覆盖发送持续运行消息、运行中确认无 Edit、Stop、释放并恢复 provider runtime、等待 idle、Edit 可见及编辑器预填原文。
- 已确认事实：App 资格模型仍要求 agent idle、最新消息非 optimistic、`replayKind === "text_only"`、文本非空且无图片/附件；本次未放宽这些安全门禁。
- 已确认根因：取消前 canonical 用户行已有 `providerMessageId` 与 `replayKind: "text_only"`；provider runtime 恢复后，同一条历史用户消息以新 ID 回放且不再携带 `replayKind`，严格 ID 比较会清空 `lastReplayableUserMessageId`，导致新回放行失去 Edit 资格。
- `grilling` 结论（如使用）：`N/A`。
- 风险与未知：根因已由精确 RED 与边界证据确认；无法证明历史项同一性时仍必须保持 provider ID 和已确认历史的 fail-closed 约束。

## 5. 执行与变更记录

- 实际改动：Playwright 场景在 Stop 后释放并恢复 provider runtime，验证同一消息重新显示 Edit 且编辑器预填原文；Seed client 补齐既有 `closeAgentRuntime` 契约；mock provider 通过两个 opt-in feature 保留恢复历史并模拟取消后用户消息 ID 漂移；AgentManager 读取最新历史用户项，仅在旧 canonical 行具备 `text_only` proof、仍是最新用户行、文本完全相同且时间戳偏差不超过 5 秒时，把 replay proof 迁移到新 provider ID，否则继续清除资格。
- 偏差与用户决策：原有 mock 只执行 Stop 不会复现生产观察到的 runtime 恢复和 ID 漂移，因此在同一已批准 Playwright public seam 内加入 opt-in provider 行为；未新增内部测试 seam，未放宽附件、运行中、optimistic 或只读门禁。
- 可证伪假设：① provider 恢复后 ID 漂移导致严格比较清除 proof，预测 canonical 与 history 文本/时间一致但 ID 不同，已确认；② agent 未回 idle，预测 idle/composer 断言失败，已排除；③ optimistic 用户行未退休，预测 canonical 最新行仍为 optimistic，已排除；④只读或能力门禁丢失，预测正常历史消息也无 Edit，已排除；⑤ provider 真正产生了更新用户消息，预测 canonical 存在更新用户行，已排除。
