# Relay 配对、E2E 加密与远程连接 CodeMap (feature)

> Security-sensitive route from pairing offer to a normal daemon Session over an untrusted relay.

## 1. Orientation

- Goal: 定位 pairing offer/QR、daemon/client relay sockets、E2EE handshake、opaque forwarding、重连和普通 Paseo WebSocket session 的完整链路。
- Scope: persistent daemon keypair、offer V2、App host profile、relay protocol v2 control/data sockets、Curve25519 + XSalsa20-Poly1305、transport reconnect/session reuse。
- Non-Scope: direct TCP auth 具体实现、Hub relationship（不走 relay）、push/voice业务、relay 部署发布流程。
- Primary question: “扫码后，客户端如何确认目标 daemon、如何让不可信 relay 只转发密文，并在断线后恢复普通 daemon session？”
- Confidence:
  - confirmed: offer schema、key storage、client/daemon handshake、relay v1/v2 routing、fatal crypto branches、reconnect tests和安全合同已由源码复核。
  - inferred: 端到端延迟和可用性依赖当前托管 relay、网络和 Cloudflare/Fly cutover 状态。
  - unknown: [`wrangler.toml`](../../packages/relay/wrangler.toml) 当前设置 `PASEO_RELAY_UPSTREAM`，实际生产请求是否执行本仓库 Durable Object 或转发到 upstream 取决于部署环境。

### Node: Main Flow

- Type: `flow`
- Status: `confirmed`
- Purpose: 固定 trust、routing、crypto 和 application handshake 的顺序。
- Route:
  1. [`loadOrCreateDaemonKeyPair`](../../packages/server/src/server/daemon-keypair.ts) loads or generates a persistent Curve25519 keypair at `$PASEO_HOME/daemon-keypair.json`; private-file helper enforces private permissions where supported。
  2. [`createConnectionOfferV2`](../../packages/server/src/server/connection-offer.ts) combines stable `serverId`, daemon public key and public relay endpoint/TLS; `encodeOfferToFragmentUrl` puts it in a URL fragment so the web server does not receive it。
  3. App scanner/link modal decodes and Zod-validates the offer, probes the connection, then [`HostRuntimeController.upsertConnectionFromOffer`](../../packages/app/src/runtime/host-runtime.ts) persists a relay connection keyed by endpoint/TLS/public key。
  4. Daemon bootstrap starts [`startRelayTransport`](../../packages/server/src/server/relay-transport.ts), which opens one v2 `role=server` control WebSocket for the `serverId`, waits for a valid control message, sends protocol ping keepalives and reconnects on timeout/close。
  5. App builds `role=client&v=2` URL; [`DaemonClient`](../../packages/client/src/daemon-client.ts) wraps the base WebSocket with `createRelayE2eeTransportFactory` only when E2EE is enabled and URL is a relay client URL。
  6. [`RelayDurableObject`](../../packages/relay/src/cloudflare-adapter.ts) routes by version-isolated `serverId`, assigns a `connectionId` to the client, tells the daemon control socket, and forwards any early client frames into a bounded pending queue。
  7. Daemon receives `connected/sync`, opens one `role=server&connectionId=...` data socket, and wraps it with [`createDaemonChannel`](../../packages/relay/src/encrypted-channel.ts)。
  8. Client generates an ephemeral keypair, derives a shared key from daemon public key, sends plaintext `e2ee_hello` with its public key; daemon derives the same key from its persistent secret and replies plaintext `e2ee_ready`。
  9. After ready, the client transport emits open and `DaemonClient` sends the normal Paseo WebSocket `hello`; daemon attaches the decrypted socket to [`websocket-server.ts`](../../packages/server/src/server/websocket-server.ts) as an external relay socket。
  10. Each application frame is encrypted by [`crypto.ts`](../../packages/relay/src/crypto.ts) as `[24-byte random nonce][NaCl box ciphertext]`, base64 text on the relay wire；the relay forwards without decrypting or modifying it。
  11. Daemon/client encrypted channels authenticate-decrypt to string or ArrayBuffer, so normal JSON session and binary terminal/file frames reuse the same WebSocket server/client paths。
  12. On data/control loss, relay/daemon/client close and reconnect; every client transport gets a fresh ephemeral key/handshake, while WebSocket server may reuse the logical Session by `clientId` within its reconnect grace window。
- Key Objects:
  - [`ConnectionOfferV2Schema`](../../packages/protocol/src/connection-offer.ts): public pairing payload。
  - [`DaemonKeyPairBundle`](../../packages/server/src/server/daemon-keypair.ts): persistent daemon identity/trust anchor。
  - [`EncryptedChannel`](../../packages/relay/src/encrypted-channel.ts): handshake/open/closed state, encryption queue and fatal errors。
  - [`RelaySessionAttachment`](../../packages/relay/src/types.ts): server/client role, protocol version, connection id。
  - [`RelayHostConnection`](../../packages/app/src/types/host-connection.ts): saved endpoint/TLS/public key。
- Edges / Children:
  - branches to `Branches` before offer, routing version, TLS, E2EE open and reconnect。
  - depends on tweetnacl, secure PRNG, base64, WebSocket, relay routing service, persistent local key file and App storage。
- Evidence: source route, [`SECURITY.md`](../../SECURITY.md), connection/relay e2e。
- Unknowns: operational routing behind `PASEO_RELAY_UPSTREAM` is not provable from checkout alone。
- Validation: exercise offer, crypto, routing and daemon session as separate layers before live relay test。
- Next Drill-Down: identify whether failure precedes `e2ee_ready`, precedes Paseo `server_info`, or occurs after application session is open。

### Node: Branches

- Type: `branch`
- Status: `confirmed`
- Purpose: 标出会改变 security、routing 或 reconnect 行为的条件。
- Branches:
  - Relay disabled:
    - Source: `generateLocalPairingOffer`, daemon bootstrap/config。
    - Effect: no offer and no outbound relay transport；direct connections remain separate。
    - Status: `confirmed`
  - Daemon/public TLS settings:
    - Source: bootstrap and pairing-offer config resolution。
    - Condition: `relayUseTls` vs `relayPublicUseTls`。
    - Effect: daemon-facing socket and offered client-facing socket can use different TLS settings；E2EE still protects application payload。
    - Status: `confirmed`
  - Relay protocol v1/v2:
    - Source: [`daemon-endpoints.ts`](../../packages/protocol/src/daemon-endpoints.ts), Cloudflare adapter。
    - Effect: missing version maps to isolated legacy v1 pair；v2 uses control + per-connection data sockets and multiple clients。
    - Status: `confirmed`
  - Handshake retry, same key:
    - Source: `createClientChannel`, `EncryptedChannel.handleDaemonRehello`。
    - Condition: client retries hello every 1 s before ready using same ephemeral key。
    - Effect: daemon re-sends ready without re-keying。
    - Status: `confirmed`
  - Different key on open channel:
    - Source: `handleDaemonRehello`。
    - Effect: close code 1008; never switch an authenticated open channel to attacker-chosen key。
    - Status: `confirmed`
  - Invalid/plaintext/tampered ciphertext:
    - Source: `EncryptedChannel.handleMessage`, `decrypt`。
    - Effect: protocol/decryption failure is fatal and closes transport for fresh handshake。
    - Status: `confirmed`
  - Pending before peer ready:
    - Source: `EncryptedChannel.pendingSends`, Relay DO `pendingFrames`。
    - Effect: both queues cap at 200 and discard oldest frames to prevent unbounded memory。
    - Status: `confirmed`
  - Control/data failure:
    - Source: daemon relay transport and Relay DO close handling。
    - Effect: stale control is terminated/reconnected; dropped server-data socket closes client with 1012 so it reconnects/re-handshakes。
    - Status: `confirmed`
  - Direct connection:
    - Source: Host runtime connection selection and DaemonClient transport selection。
    - Effect: direct TCP/socket/pipe does not use relay E2EE wrapper；network TLS/password policy is separate。
    - Status: `confirmed`
  - Key file unreadable/invalid:
    - Source: `loadOrCreateDaemonKeyPair`。
    - Effect: daemon regenerates identity; existing pairing links/public keys no longer authenticate it and clients must re-pair。
    - Status: `confirmed`
  - Cutover proxy:
    - Source: Cloudflare adapter default export and `wrangler.toml`。
    - Condition: `PASEO_RELAY_UPSTREAM` set。
    - Effect: worker proxies requests upstream instead of local Durable Object routing。
    - Status: `confirmed` in source; deployed value `unknown`
- Evidence: branch implementations and focused tests。
- Unknowns: deployment config and network middleboxes remain external state。
- Validation: use Branch Index tests below, then live relay only for deployment behavior。
- Next Drill-Down: never diagnose a relay routing failure solely from E2EE logs or vice versa。

### Node: Data And Dependencies

- Type: `dependency`
- Status: `confirmed`
- Purpose: 区分 trust anchor、ephemeral session material和 relay-visible metadata。
- Read First:
  - Daemon keypair: `$PASEO_HOME/daemon-keypair.json`, schema in [`daemon-keypair.ts`](../../packages/server/src/server/daemon-keypair.ts)。
  - Offer: fragment payload in [`connection-offer.ts`](../../packages/protocol/src/connection-offer.ts)。
  - Client saved connection: App `HostProfile.connections[]` with endpoint/TLS/public key。
  - Crypto: `tweetnacl` Curve25519 `box.before`, XSalsa20-Poly1305 `box.after/open.after`, 24-byte random nonce。
  - Relay metadata: `serverId`, role, version, `connectionId`, IP/timing/frame sizes and plaintext public-key handshake frames。
- Edges / Children:
  - offer transfers daemon public key out-of-band and acts as trust/capability anchor。
  - client ephemeral public key and daemon persistent secret derive one connection shared key。
  - relay routes by ids but receives no application plaintext or secret key。
  - decrypted socket feeds the same daemon Session as direct transport。
- Evidence: security doc, key/offer/channel schemas and routing attachments。
- Unknowns: within-open-session replay protection is not implemented; random nonces are not tracked by counter/set。
- Validation: key length/roundtrip/wrong-key tests, encrypted transport opacity and e2e session tests。
- Next Drill-Down: data exposure review must include App saved profiles/diagnostic redaction and relay metadata, not only cipher code。

### Node: Effects

- Type: `effect`
- Status: `confirmed`
- Purpose: 明确 pairing、open、failure和 reconnect 后的 durable/transient state。
- Effects:
  - Pairing: App persists host `serverId`, relay endpoint/TLS and daemon public key; no client secret is persisted。
  - Daemon: persistent keypair and stable server id survive restart when files remain valid。
  - Relay: stores WebSocket attachments and bounded early frames, but forwards application content opaquely。
  - Open connection: normal Paseo `hello -> server_info -> session` begins only after E2EE ready。
  - Binary/text payloads: both encrypted; ciphertext is base64 text on relay transport。
  - Failure: invalid handshake/decryption/plaintext closes transport; higher-level DaemonClient reconnects。
  - Reconnect: new ephemeral client key and shared key; logical Session may survive transport switch/reconnect via same `clientId`。
  - Observability: daemon logs relay control/data lifecycle and E2EE failures without logging decrypted payload by this layer。
- Evidence: client/daemon adapters, relay DO and websocket reconnect tests。
- Unknowns: bounded queues can intentionally drop earliest pre-open frames; normal DaemonClient waits for E2EE open before app hello, reducing this path in standard use。
- Validation: pipelined hello e2e, reconnect tests and live relay test。
- Next Drill-Down: distinguish pairing profile persistence from cryptographic session state; only the former survives App restart。

### Node: Risk And Unknowns

- Type: `risk`
- Status: `confirmed`
- Purpose: 保留安全边界，防止把 relay TLS、public key 或 reconnect 当成不相关实现细节。
- Risks:
  - Pairing link is the trust/capability anchor；泄露后持有者可建立新 client session。Treat it like a password。
  - Regenerating daemon keypair silently invalidates every prior pairing and changes daemon cryptographic identity。
  - Relay TLS does not replace E2EE；direct password does not provide relay-style payload confidentiality on untrusted transit。
  - Within-session ciphertext replay is not prevented by counters/nonces tracking；cross-session replay fails because fresh keys are derived。
  - Plaintext application JSON on encrypted channel is a fatal protocol mismatch and must remain rejected。
  - A different re-hello key on an open daemon channel must never trigger re-key in place。
  - Relay sees metadata (IP, timing, sizes, ids, public-key handshake) even though content is opaque。
  - Pure-JS NaCl encryption + base64 runs on daemon/client main loops and can increase terminal latency。
  - Bounded 200-frame queues trade oldest pre-open data for memory safety；changing this needs an explicit delivery contract。
  - Current source supports Cloudflare DO and upstream cutover; production topology must be confirmed externally before deployment conclusions。
- Unknowns:
  - No mapped key rotation/revocation mechanism beyond deleting/regenerating and re-pairing。
  - No within-session replay defense is present as of this map date。
- Next Drill-Down: security changes require crypto/channel unit tests plus real end-to-end handshake; routing changes require DO/control/data tests separately。
